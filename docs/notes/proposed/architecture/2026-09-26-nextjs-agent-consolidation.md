# Agent Note: Next.js 统一 AI 执行，微服务归档退役

Status: proposed

## Problem

现役项目同时有 AG-UI/独立 Agent 与 Next.js 悬浮 AI SDK 链路，工具、会话、批准和保存状态分叉。客户端先改 RHF 再保存再补版本，无法保证修改与历史一致；位置地址也会在重排后误指目标。

2026-09-26 用户明确要求：只保留 Next.js + Vercel AI SDK 入口，移除微服务线上与部署路线，通过已有 SSH 清理相关容器；旧源码保留归档，并改进提示词建议质量。

## Proposal

采用[总体规格](../../../superpowers/specs/2026-09-26-nextjs-agent-consolidation.md)和[切片执行入口](../../../superpowers/plans/2026-09-26-nextjs-agent-execution.md)：Web 统一模型运行、业务工具、持久 Run 与文档提交；稳定条目 ID、revision/CAS、幂等回执、原子留痕。保留悬浮/停靠 UI，所有短 AI 能力同样迁入 Web。

独立 Agent/旧 AG-UI 路线归档至 `archive/agent-microservice/2026-09-26`，从在线 import、workspace 和部署 workflow 中退出。实际容器清理在新生产全能力通过后执行；已核实 agent_default 网络有其他业务共享，所以仅移除三目标容器，保留网络和卷。

这是对[旧运行时决定](../../implemented/architecture/2026-06-16-agent-runtime-ag-ui-over-ai-sdk.md)的拟议翻转。旧文记录一次真实回退，不能抹掉。新方向来自用户明确选择，并以有界执行、提交一致性、能力覆盖和阶段验证防止重现旧回归。当前旧实现仍在运行，所以旧 Note 暂不伪装为已归档，新 Note 暂不标 implemented。

## Alternatives considered

- **保留 AG-UI 与独立服务，统一两个 UI**：能保留直接数据面和长请求环境，现有基础最多；但仍维护专属主机、JWT、Redis 与部署，用户明确要求退出该路线，因此不采用。
- **只改善现有 Next.js 提示词，不重构写入**：成本低、能先改善表达；但不能解决错条目、虚报保存和无痕修改，提示词改进必须与可靠提交配套。
- **加入持久工作流/新 worker 支撑无限后台任务**：可提供长时间运行恢复；代价是新依赖、配置与运维，用户本轮选择单一 Next.js 路线且没有要求无限后台，首期采用有界请求与检查点。
- **切换数据库到长连接并使用交互事务**：事务代码直观；但现有 Neon HTTP 路径是实际约束，全面换驱动会扩大影响，首期使用跨现有驱动可执行的单条参数化 CTE，并通过真实 DB 验证。

## Acceptance criteria

- 两套旧链路只剩 Next.js 现役；所有聊天/润色/Helpers 无 Agent 地址依赖。
- 提交、修订与回执原子；稳定 ID、冲突、重试、条件撤销有行为测试与真实事务证据。
- 提示词在固定合成集的实际对照中通过硬约束和有效性门禁；未测就不宣称改进。
- UI 状态可由持久事件还原，无成功假象、重复应用或旧提案覆盖。
- 归档原文及清单完整；生产专属容器退役但共享网络/无关业务无变化。
- 执行阶段通过仓库全部 DoD；本次文档工作不替代业务验证。

## Risks

Vercel 函数有限时，需有界执行与重新续做；BYOK key 不落检查点，丢失 session 后需要重新连接模型。稳定 ID 与 revision 会影响所有 writer，不能回滚到旧覆盖式写入。归档后的旧实现仍有已知缺陷，不能从归档直接恢复生产。

收益是减少执行分叉、运维路线和保存歧义；代价是需改造多个现役写入口、完整迁移能力并补真实故障测试。若出现无法在函数预算内完成的高频任务，再单独评估持久工作流；若回执延迟影响编辑，先测量事务/网络瓶颈，不撤销幂等与版本保护。

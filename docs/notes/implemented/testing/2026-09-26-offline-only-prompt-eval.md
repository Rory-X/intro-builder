# Agent Note: 提示词评测只做离线的一半，真实对照标 not_run

Status: implemented

## Problem

P05 任务 6 要求「执行离线和真实对照评测」：离线校验契约、越权、
「无保存却称已保存」；真实对照用同一模型、同参数、同工具、每例 3 次比较
旧/新 prompt（spec §8 算出 16×2×3=96 次有界请求）。

问题在于**真实对照需要显式可用的评测配置**（模型凭据 + 预算）。
当前环境没有这样的配置，而 spec §8 写着一句硬要求：

> 真实评测未跑时标 `not_run`，不可提交假定分数。

因此这段工作天然分两半：一半现在能做且 CI 可跑，另一半必须等配置。
**混在一起做**是最容易发生的错误 —— 用机械检查冒充质量评分，
让「通过率」看起来有内容。

## Decision

只实现离线的一半，并把「另一半没跑」变成代码里的事实。

### 1. 评测集：16 例合成场景，每例带硬失败条件

`evals/resume-advice-cases.json` 按 spec §7 逐条落地 Q01–Q16。每例四个字段缺一不可：

- `facts`：可写入的事实清单（判断「是否编造」的唯一依据）；
- `allowedActions`：本例允许的动作集合；
- `forbidden`：明确禁止的行为；
- `hardFailure`：任一命中即整体不通过。

### 2. 自洽性检查防「虚增通过率」

`validateEvalCases` 检查用例数、ID 唯一、以及**每例的 `forbidden` 与
`hardFailure` 非空**。

最后一条是关键：一个 `forbidden` 为空的用例**永远不会失败**。
如果评测集里有几例这样的，通过率的分母就被虚增，数字变得没有意义 ——
而这种缺漏在人工翻阅 JSON 时极难发现。

### 3. 机械筛查只作提示，不作判据

`findFabricationHints` 找输出里新出现的「提升 N%」「提升 N 倍」类表述。

**它不是通过判据**，因为 spec §8 明确写着「不能用禁词扫描代表『无编造』」。
它是给人看的提示：命中时值得人工看一眼。

实现上有一条关键细节：**先排除输入里已经存在的数字**。
Q14 的输入是「从 2.4s 降到 1.1s」且要求保留 —— 若把输出里重复出现这些数字
报成编造，这条判据立刻变成噪音，而噪音会被忽略，等于没有。

### 4. `liveComparison` 永远是 `not_run`

报告里的 `liveComparison` 字段是字面量类型 `"not_run"`，且有专门断言钉住。

这让「真实对照没跑」成为**类型层面的事实**而不是一句注释：有人想让离线 runner
返回分数，必须先改那条测试并解释为什么。

## Alternatives considered

- **不做评测，等配置齐了一次做完** — 最省事，也最诚实（不会产生误导性数字）。
  否决原因：离线那半（契约自洽性、评测集完整性、机械筛查）**不需要凭据**，
  且正是最容易出错的部分（缺 forbidden 的用例、把 Q14 的数字误报为编造）。
  把它们和真实对照捆在一起，等于让可做的部分也一起等。
- **让离线 runner 接收模型回复并给出「通过/不通过」** — 接口更统一，
  未来接真实对照时改动更小。否决原因：那会诱导调用方把「机械筛查通过」
  当成「质量通过」。spec 明确禁止这种替代。
- **用 LLM 当评审员（LLM-as-judge）代替人工语义检查** — 听起来能自动化软评分。
  否决原因：spec §8 要求「自动规则和人工语义检查**分别记录**」，
  且软评分涉及中文自然度与遵循用户约束，这些用另一个模型打分会引入
  「评审模型与被评模型同源」的偏差，且结论无法复核。更重要的是当前没有评测配置。
- **禁词筛查里不做「排除输入已有数字」** — 实现更简单（直接扫输出）。
  否决原因：会把 Q14 的正确答案报成编造。判据一旦产生假阳性就会被忽略，
  而「会被忽略的检查」等于没有检查。
- **把评测集写成 TypeScript 常量而不是 JSON** — 有类型检查，编不出格式错误。
  否决原因：spec 的产出清单明确要求 `evals/resume-advice-cases.json`；
  JSON 也更便于把结果交给非工程师（产品/设计）核对场景是否覆盖真实用户问题。

## Consequences

- **收益**：CI 能验证评测集本身没有缺漏；「真实对照未跑」在类型上是事实；
  机械筛查有防止假阳性的处理，因此它的输出值得看。
- **代价**：评测能力只覆盖一半，真正回答「候选稿是否优于旧稿」还需要评测配置。
- **已知上限（明确不假装完成的部分）**：
  - **真实模型对照未运行**（`not_run`）。候选稿相比旧稿的质量提升**没有证据**。
    本切片也不声称它更好。
  - 软评分五项（具体性、证据相关性、动作可执行性、中文自然度、遵循用户约束）
    与阈值（平均 ≥ 8、至少 60% 案例严格改善）均未执行。
  - 离线部分**未**包含「越权 / 无保存却称已保存」的行为红→绿 ——
    那些属于任务 3，需要真实工具与状态机参与；当前的离线 runner 只做
    评测集自洽性与机械筛查。
  - `token / 首可见反馈 / 总耗时 / 无效工具调用数` 等指标未采集（需真实对照）。
- **什么信号发生时该重访**：拿到评测配置后，实现 `eval:ai:live`：
  同一模型与工具、每例 3 次、并发 1、固定 output budget；
  先在合成输入上跑（不产生真实简历写入），结果写机器可读文件 + 短报告。
  若发现某例在候选稿上**退化**，按 spec §8 记录例外证据并重新评审阈值，
  **不篡改结果凑过线**。
- **另一条重访信号**：若有人开始在 CI 里读取「通过率」，先确认它读的是哪一半 ——
  离线那半的数字不代表质量。

## Verification

- `apps/web/tests/unit/ai-eval-offline.test.ts`（19 例）：
  - **评测集**：至少 16 例、覆盖 Q01–Q16 全部 ID、自检无问题、
    每例 hardFailure/forbidden/facts 非空、ID 唯一；
    自检能发现缺 hardFailure、ID 重复、用例数不足三种缺漏；
    Q11 的硬失败指向权限/泄密；
  - **机械筛查**：找出新出现的百分比与倍数、**先排除输入已有数字**
    （Q14 场景返回空）、同一表述不重复报、无量化表述时不报；
  - **报告**：用例数与自检问题、`liveComparison` 永远是 `not_run`（三处断言）、
    模拟回复只产出提示不产出分数、未知用例被忽略。
- 全量：`pnpm test` 1308 例通过、`typecheck` 四包全绿、
  `lint` 0 error（12 warning = 基线）、`build` 通过。

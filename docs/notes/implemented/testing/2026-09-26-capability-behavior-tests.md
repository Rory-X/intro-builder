# Agent Note: 五个能力场景用「编排层行为」验证，而非提示词措辞

Status: implemented

## Problem

P05 任务 3 要求「对『诊断』『润色』『目标岗位』『缺事实』『拒绝后继续』
各做行为红→绿；工具错误时返回真实状态而不编造结果」。

这里有一个容易做错的判断：**「行为」指什么？** 最省事的做法是断言
「提示词里包含『不要编造』这句话」，但那种测试毫无价值 ——
提示词写了什么与模型实际做了什么之间没有等价关系，
而且它会在有人调整措辞时无意义地变红。

真正要验证的是**编排层真的做了什么**：有没有产出文档修改、有没有结束本轮
等用户、失败时有没有如实回报。

## Decision

测试断言编排层的**可观测行为**，判据取自 spec §4 的
「有效工具输出 / 禁止行为」表。

用 `orchestrateRun` + 全注入依赖驱动，每个场景断言三类事实：

1. **是否发生文档写入** —— 依据 `mutation.committed` 事件是否存在，
   **不是**看模型说了什么、也不是看工具自称成功。
2. **是否结束本轮**（等待用户）—— 依据 `endType === "run.waiting_user"`。
3. **失败时是否如实回报** —— 依据 `tool.failed` 事件及其 `code`。

五个场景各自的判据：

| 场景 | 意图 | 关键断言 |
|---|---|---|
| 诊断 | `diagnose` | **不发生文档提交**（只读） |
| 润色 | `rewrite` | 有真实回执才 `committed`；**无回执的成功不算已保存** |
| 目标岗位 | `role_match` | 只读时不写文档；约束禁止把 JD 技术写进技能 |
| 缺事实 | `fact_intake` | `askUser` 后 `endType` 为 `waiting_user` 且不写文档 |
| 拒绝后继续 | — | 工具失败发出 `tool.failed` 并带 `code`；不产生 `mutation.committed` |

### 两个最有价值的断言

**「工具声称改了但无回执 → 不算已保存」**：这是 P02/P03 反复修过的同一类
假成功。工具返回 `{ status: "succeeded", result: { saved: true } }` 但**没有**
`mutationId` / `revision` 时，编排层不得发出 `mutation.committed`。
这条断言把「模型完成 ≠ 已保存」钉在行为层面。

**「提交前被取消 → 不执行工具」**：`isWritable` 返回 false 时工具执行次数
必须为 0。取消与提交可能并发，只有执行前再核验一次，才能让
「取消先成功则禁止提交」成立。

另外补了一条「一次工具失败不终止整轮」——被拒绝的建议不该让整个流程停下来。

## Alternatives considered

- **断言提示词文本包含某些句子** — 实现最快，不需要编排层。
  否决原因：那验证的是「我写了这句话」，不是「模型会这么做」。
  更糟的是它会在有人调整措辞时无意义地失败，训练出「改测试让它过」的习惯。
- **用真实模型跑这五个场景** — 最贴近真实行为。否决原因：需要评测凭据
  （当前没有），且模型输出有随机性，断言会不稳定。真实对照是任务 6 的
  独立工作，不该把它塞进单元测试。
- **只断言意图识别（`resolveIntent`）而不跑编排层** — 更轻量。
  否决原因：意图识别对不等于行为对。「诊断不写文档」这件事必须在
  编排层验证 —— 意图约束是文本，而工具执行是代码，两者之间没有保证。
- **把「无回执不算已保存」的检查留给 P04 的既有测试** — 避免重复。
  否决原因：那条不变量值得在**能力场景**里也钉一次。它的失败模式
  （用户看到「已保存」但内容没变）代价极高，多一处防线不算冗余。
- **让 `askUser` 用 `succeeded` 状态返回**（我第一版就是这么写的）—
  否决原因：实测发现编排层只在 `asked` 状态下发出 `run.waiting_user`
  并**跳出流消费**。用 `succeeded` 会让模型在 askUser 之后发起的写工具
  也被执行 —— 用户还没回答，文档已经被改。

## Consequences

- **收益**：五个场景的核心不变量（不写文档 / 不伪造保存 / 追问即停 /
  失败如实回报）有了机械防线；判据基于事件而非文本，因此调整提示词措辞
  不会误伤它们。
- **代价**：这些测试需要构造 `orchestrateRun` 的完整注入依赖（约 40 行 harness），
  比断言字符串重得多。这是为「验证真实行为」付的必要成本。
- **已知上限**：
  - **未验证模型的实际输出质量**。这些测试用假流（`SdkStreamPart[]`）驱动，
    因此验证的是「编排层在各种工具结果下的行为」，不是「模型会给出什么样的建议」。
    后者属任务 6 的真实对照。
  - 「候选禁止只用『突出亮点、加强量化』代替可用方案」这条只通过
    `INTENT_CONSTRAINTS` 的文本断言覆盖，**没有**行为层面的验证
    （那需要真实模型判断）。这一点必须如实说明，不能因为有一个文本断言
    就声称已经验证。
  - 五个场景覆盖的是单轮行为；多轮（拒绝后下一轮是否换 ID 重提）由
    P04 的审批路径测试覆盖。
- **什么信号发生时该重访**：若真实对照（任务 6）发现模型在某场景的系统性
  偏差（例如总是给泛化建议），应把该场景的判据从「编排层行为」
  扩展为「回复内容规则」，但那需要评测配置。

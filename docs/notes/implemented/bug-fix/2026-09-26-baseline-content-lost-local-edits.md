# Agent Note: `advance-baseline-only` 会静默丢弃用户输入 —— 基准必须是服务端内容

Status: implemented

## Problem

上一个提交（`2026-09-26-floating-new-path-wired.md`）把浮窗接到新路径时，
我为「本地有未提交编辑」这条分支写了这段：

```ts
if (plan.action === "advance-baseline-only") {
  runBridge.applyRemoteCommit({
    content: getResumeContent(),   // ← 本地当前内容（含用户未保存的编辑）
    revision: plan.revision,
  });
  toast.message("服务端已更新内容，你还有未保存的修改，已保留你的输入。");
}
```

而 `SyncPlan` 的该分支**不带 `content`**，所以调用方只能自己找内容 ——
我选了本地内容（因为「表单不该被覆盖」这个念头主导了写法）。

### 这是静默数据丢失

`applyRemoteCommit` 把传入的 `content` 设为**已确认基准**：

```ts
const applyRemoteCommit = useCallback((next) => {
  setBaseline({ content: snapshotContent(next.content), revision: next.revision, … });
  // 有本地输入时不动表单
});
```

而后续提交的 operations 由 diff 计算：

```ts
const diff = buildMutationOperations({ baseline: baseline.content, next: getContent(), … });
```

**基准 = 本地当前内容（= 表单内容）⇒ diff 恒为空** ⇒ 用户那些编辑
**永远不会被提交**。

而界面上一切正常：内容还在表单里、状态回到 idle、toast 还说
「已保留你的输入」。**用户刷新后改动才消失。**

## Decision

把「基准内容」与「表单是否被覆盖」两件事分开：

1. **`SyncPlan` 的 `advance-baseline-only` 也带上 `content`**（服务端内容，
   与 `sync` 同一份）；
2. **判定顺序调整**：先检查内容是否可得，再判断有无本地编辑。

| 情况 | 表单 | 基准 |
|---|---|---|
| 无本地编辑 | 覆盖为服务端内容 | 服务端内容 |
| **有本地编辑** | **保持用户输入** | **服务端内容** |
| 取不到内容 | 不动 | 不动（`reload`） |

于是用户那次提交的 diff 会**涵盖他的本地编辑**，由服务端 CAS 决定是否冲突
（而不是把它们当成已保存而丢弃）。

### 判定顺序为什么必须调整

第一版把「有本地编辑」放在内容检查**之前**，那条分支就注定拿不到内容 ——
调用方只能自己找一个顶上，而唯一可用的就是本地内容（危险的那个）。
**顺序错误直接导致了错误的选项集。**

调整后两个分支共享同一个前置条件（内容可得），区别只剩「表单要不要覆盖」——
那是这条判据真正要表达的唯一区别。

### 连带修正：取不到内容时即使有本地编辑也 `reload`

原实现有一条断言「有本地编辑时即使取不到内容也不 reload（基准仍要推进）」，
理由写的是「基准推进不需要内容」。

**那个理由是错的**：推进基准必须知道**新基准的内容是什么**。
不知道就只能拿本地内容顶上 —— 正是上面那个静默丢失。

因此该断言改写为「取不到内容时即使有本地编辑也 reload」。

## Alternatives considered

- **保持 `advance-baseline-only` 不带内容，让调用方传本地内容**
  （我第一版的做法）— 接口更简单，且「不覆盖表单」的意图看起来更直接。
  否决原因：那正是数据丢失的来源。它把「基准用什么」这个关键决定
  推给调用方，而调用方在那一刻只有本地内容可选 —— 这是接口设计的缺陷，
  不是调用方的疏忽。
- **`advance-baseline-only` 干脆不推进基准** — 最保守，绝不丢数据。
  否决原因：不推进基准会让用户那次提交仍以**旧** revision 发送，
  必然被服务端 CAS 拒绝成冲突 —— 用户会看到「冲突」而实际只是
  「AI 也改了同一份文档」。推进基准才对。
- **把服务端内容与本地内容合并后作为基准** — 看起来能两全。
  否决原因：合并在字段级别需要三方 diff（base/server/local），
  而这里的信息不足以判断「哪些本地改动是相对服务端的」。
  当前做法（基准=服务端、表单=本地）让 diff 自然算出该合并的内容。
- **保留原判定顺序，只在「有本地编辑」分支里补内容检查** —
  改动更小。否决原因：两个分支会各写一份内容检查，而它们的判据本该相同。
  共享前置条件（先检查内容）更简洁，也从结构上避免了「某条分支忘了检查」。
- **只在组件里改（不动 `SyncPlan`）** — 一处改动。
  否决原因：组件仍拿不到服务端内容（`SyncPlan` 不给），
  只能去 `loadServerContent` 再拉一次 —— 多一次网络往返，
  且与 `floating-run` 内部已经取到的内容重复。

## Consequences

- **收益**：静默数据丢失被消除；`SyncPlan` 的形状让「基准=服务端内容」
  成为**契约强制的**（而非调用方要记得做的事）；
  两个分支的差别被收窄为唯一真正的区别（表单是否覆盖）。
- **代价**：`SyncPlan` 的该分支多一个 `content` 字段；
  测试的 3 处断言需随之更新（其中 1 处的**前提**本身就是错的）。
- **已知上限**：
  - **`runBridge` 仍未由 `editor-client.tsx` 提供**，因此这条修正
    在当前代码路径上**还未被执行到**（新路径尚未真正启用）。
    但契约与组件两侧都已改对 —— 接线时不会再踩这个坑。
  - **未做真实浏览器验证**：这类「diff 恒空」的失效只能在真实交互里观察到，
    单测覆盖的是决策逻辑而非端到端行为。
  - **三方合并仍未实现**：本地编辑与服务端改动落在**同一字段**时，
    当前会由服务端 CAS 返回冲突（用户需手动处理）。
    不相交字段的自动 rebase 是更好的体验，但需要 base 版本参与比较。
- **什么信号发生时该重访**：若用户反馈「改了一些内容、AI 也改过之后
  我的改动没了」，先查这条：基准是否被设成了本地内容。
  若要实现不相交字段的自动 rebase，需要把 base 版本
  （上次确认基准的内容）也保留下来做三方比较。

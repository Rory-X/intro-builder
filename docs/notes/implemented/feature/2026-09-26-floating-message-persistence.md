# Agent Note: 新路径不写会话表 —— 刷新后对话历史里看不到那些消息

Status: implemented

## Problem

核实刷新恢复时发现：**统一 Run 路由完全不写浮窗会话表**
（`agent_floating_chat_message`），而旧路径一直在写。

后果很具体：用户用新路径聊完、**刷新页面**，按会话恢复的对话历史里
**看不到那些消息**。界面看起来像「那次对话没发生过」。

注意这不是「Run 无法恢复」：Run 自身状态与事件可从
`GET /api/ai/runs/[runId]?events=1` 读到。缺的是**展示用**的会话历史
（用户看到的聊天记录）—— 两者是不同的东西，不能因为后者能恢复就忽略前者。

## Decision

新增 `lib/ai/floating-persistence.ts`（纯函数）+ 在流收尾处写入。

### 1. 投影做成纯函数

投影规则有几个具体判断，而它们原本会落在「服务端流收尾」这个难以单测的位置：

- 文本如何累积（`text.delta` 拼接）；
- 工具卡取哪个状态、同一工具多次事件如何合并；
- 哪些事件不入库（`attempt.started` 等无内容事件）；
- 空内容的判据（文本、工具、问题**三者都空**才不写）。

抽成纯函数后可穷举（24 例）。

### 2. `running` 的工具卡**不入库**

这是与旧路径对齐的一处（`persistedToolCalls` 会过滤掉 `running`）。

必要性：存的若是 `running`，刷新后那条工具卡会**永久转圈** ——
没有任何后续事件会再更新它（那一轮已经结束）。

因此「只有 running 工具且无文本」的那一轮**整条不写**（否则会写一条
内容为空、只有转圈工具卡的消息）。

### 3. 工具状态**不倒退**

事件可能乱序到达（重放、并行工具）。让后到的 `tool.started`（running）
覆盖已完成的 `completed`，同样会让历史里的工具卡永久转圈。

### 4. 不透传工具原始结果

`payload.result` 可能含简历完整快照。让它进库等于把整份文档又存一份
（且历史页会渲染它）。测试里有专门断言（构造 `{ resumeSnapshot: … }`
确认不出现在结果里）。

### 5. 持久化失败**不冒泡**

对话内容已推给客户端、文档已原子落盘。留痕写入失败只是「历史里少一条」，
不该让整个响应变成错误 —— 那会让用户以为 AI 没做完，而实际改动已在。

用 `console.error` 而非静默吞掉：留痕缺失是可观察的故障，排查时需要日志。

### 6. `continue` 路由的 sessionId 取自**已落库的 Run 行**

不取自请求体。客户端换一个 `sessionId` 就能把这一轮挂到**别的会话历史**上，
那是越权写入。

## 实测修正：`sessionId` 没传下去（持久化曾是死代码）

我在执行层加了 `sessionId?: string | null` 字段并写了持久化逻辑，
**但没在路由里传它** —— 于是那段代码永远不会执行。

**而全量测试仍然全绿**（1775 例）—— 因为它们测的是纯函数投影，
不测「路由是否真的把它传下去」。

补了两条路由层断言把这件事钉住。这是本提交最值得记的一点：
**「纯函数测过」与「链路上真的用了它」是两件事** ——
前者全绿不能推出后者，而后者恰恰是这类改动的成败所在。

## Alternatives considered

- **在客户端持久化**（组件把消息 POST 回会话路由）— 不需要改服务端。
  否决原因：客户端在流结束后才知道完整内容，而那时用户可能已经关闭页面 ——
  消息丢失。服务端在收尾时写入更可靠（它本来就在处理终态）。
- **从库里重读事件再投影**（而不是在 `send` 里累积）— 少维护一个数组。
  否决原因：多一次查询；且 `attempt.started` 之前的事件不属于本轮，
  而本轮边界恰好就是这个数组的生命周期。
- **持久化 `running` 的工具卡**（保持与实时流一致）—
  否决原因：刷新后永久转圈。实时流里它会继续更新，库里不会。
- **持久化失败时向上抛**（让调用方知道）— 更「响亮」。
  否决原因：内容已落盘、已推流。为一条留痕失败而把响应变成错误，
  会让用户以为整轮失败。日志足够。
- **`continue` 路由从请求体取 sessionId** — 与 `start` 一致。
  否决原因：那是越权入口 —— 客户端可以换一个 sessionId 把回答挂到
  别人的会话历史上的（虽然仍受 userId 约束，但会话归属会错乱）。
  已落库的 Run 行才是权威来源。
- **把 sessionId 做成 `streamRunAttempt` 的必填参数** — 类型更强。
  否决原因：`sessionId` 本身可空（不是所有调用方都有会话），
  必填会迫使每个调用点传 `null`，那和可选没有实质区别。

## Consequences

- **收益**：新路径的对话终于会出现在刷新后的历史里；工具卡不会永久转圈；
  原始载荷不进库；留痕失败不破坏主流程。
- **代价**：多一个模块（约 200 行 + 24 例测试）+ 两条路由各传一个参数。
- **已知上限**：
  - **未做端到端验证**：本提交验证的是「投影正确」与「参数被传下去」，
    没有验证「写入后能正确读回并渲染」。那需要真实数据库往返
    （集成测试）或人工冒烟。
  - **未接线刷新恢复的读取侧**：`restoreWorkspace`（读 Run 事件做恢复）
    仍未接入浮窗。当前补的是**展示用历史**的写入，
    而「刷新后 Run 状态如何恢复到界面」是另一条路径。
  - **默认 surface 仍是 `"panel"`**：浮窗即使具备能力，用户默认仍看不到它。
  - **工具卡的 `summary` 为空**：旧路径持久化的是工具执行时算好的摘要，
    而新路径的事件里没有它（只有 toolName）。历史页会显示空摘要。
    要修需要在执行层把摘要一并写进事件 payload —— 属后续工作。
- **什么信号发生时该重访**：若用户反馈「刷新后 AI 的回复不见了」，
  先查 `sessionId` 是否被传下去（本提交修的就是这个）。
  若历史里的工具卡显示为空标题，那是上面提到的 `summary` 缺口。

## Verification

- `apps/web/tests/unit/ai-floating-persistence.test.ts`（24 例）：
  - **助手投影**：累积文本、三空不写、**工具已完成但没说话也写**、
    **只有 running 工具且无文本 → 不写**；
  - **工具卡**：succeeded → completed / failed → error（running 被过滤）、
    **状态不倒退**、同一工具合成一条、缺 toolCallId 跳过、
    **不透传原始结果**（含泄漏断言）；
  - **等待问题**：带出问题与 id、缺 id 或缺文本不入库、只提问也写；
  - **parts 形状**：文本在前工具与问题在后、无文本时不含 text 条目、
    id 稳定可推导；
  - **用户消息**：保留内容、trim、空消息不产生记录；
  - **会话标题**：取前 50 字符、短消息原样、两处规则同源；
  - **纯函数**：同输入同输出、不改动入参。
- `apps/web/tests/unit/ai-run-route-history.test.ts`（17 例，含新增 2 例）：
  **sessionId 被传给执行层**（注明「否则持久化是死代码」）、
  未提供时传 null。
- 全量：`pnpm test` 1775 例通过、`typecheck` 四包全绿、
  `lint` 0 error（12 warning = 基线）。

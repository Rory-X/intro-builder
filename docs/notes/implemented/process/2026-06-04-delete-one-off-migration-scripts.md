# Agent Note: 一次性迁移脚本用完即删，不留在仓库当 seed

Status: implemented

## Problem

模板 v2 重构期间，`scripts/seed-builtin-templates.ts` 把旧的 React 硬编码模板转写成 HTML+CSS 塞进 DB，`db/seed/template-abbey-stub.ts` 是早期验证用的 stub。重构上线后它们都失去了用途，但仍然留在 `scripts/` 里——因为「seed 脚本保留在仓库」被当成了默认标准做法。

这类文件的实际风险不是占几 KB，而是**它们会腐蚀对其用途的判断**：后来的人（和 Agent）看到 `scripts/seed-*.ts` 会以为「跑它是环境初始化的一部分」，于是照做——把一个已经过期的迁移逻辑再跑一遍，或在写新 seed 时模仿它的写法。这类脚本也因此长期无人敢删。

## Decision

**一次性迁移 / 验证脚本在其目标完成后即删除，不保留在仓库。** 判断依据是文件的实际用途，不是命名或所在目录：

- 目标已完成（迁移上线、重构收尾、事故已复盘）且不会再跑的 → **删除**。历史由 git 承载，不需要留一个不能跑的文件占位。
- 需要持续使用的环境初始化 / 数据校验（如 `scripts/verify-templates.ts`、`scripts/db/check-users.ts`）→ 保留，并说明它什么时候该跑。

`5f282c52c` 收尾时按此清理了 `scripts/seed-builtin-templates.ts`、`db/seed/template-abbey-stub.ts` 等一次性产物。

**做删除决定前先确认目标真的完成了**：查 git 历史确认它服务的那次改动已合入，并确认没有别处还在引用它（`grep` 文件名）。删错了比留着更糟——留着的成本是困惑，删错的成本是流程断掉。

## Alternatives considered

- **保留所有迁移脚本作为「历史参考」** — 零判断成本，且理论上能回看当初怎么迁移的。但 git 已经保留了完整历史（且带 commit message 说明动机），在 `scripts/` 里再留一份可执行副本是冗余的；更糟的是它看起来可执行、实际已过期，会主动误导。放弃。
- **移进 `scripts/archive/` 之类目录统一存放** — 比散落原地方便识别为「历史」。但归档区一旦建立就会无限增长，且「已归档」需要额外维护（谁来判断该移进去、何时清理），收益不抵成本。历史归 git 即可。
- **在脚本头部加注释标明「已过期，勿运行」** — 成本最低。但注释没有任何机械约束，且可执行文件的存在本身就在邀请人运行它；这属于「写在散文里的规矩」。

## Consequences

- **收益**：`scripts/` 里留存的每个脚本都可安全执行，不必先考古判断它是否过期；减少「照着旧迁移脚本再跑一遍」这类事故。
- **代价与已知上限**：依赖改动者在收尾时主动清理——**这一步没有任何自动门禁**，检查是否过期是语义判断。**重访触发条件**：若再次出现「已过期的一次性脚本被误当作常规 seed 运行」的事故，应考虑给 `scripts/` 加一条可机械检查的约定（例如要求每个脚本在头部声明用途与失效条件）。

## Verification

- 现存脚本清单与其用途：`scripts/db/`、`scripts/dev/`、`scripts/templates/`、`scripts/notes/`；各目录的说明见 `scripts/README.md`。
- 回归方式：新增脚本时问一句「它的目标完成后还需要它吗」；收尾时对本次新增的脚本复查一次，过期的删除。

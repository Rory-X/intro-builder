# Agent Note: 退役审计做成棘轮测试，而不是文档里的主张

Status: implemented

## Problem

P07 任务 2 要求「完成能力矩阵……预览环境完全不配置 Agent URL/JWT/Redis 仍可使用；
删除请求 fallback，不以旧服务兜底掩盖缺能力」。

但「能力矩阵已完成」如果只写在文档里，它是一个**主张**而不是**事实** ——
没有任何东西阻止下一个人在新增路径时又去调旧服务。而这类回退极难在评审时
发现（新增一个 `createAgentClient()` 调用看起来完全合理）。

核实过程中也确实发现了两个之前没被记录的事实：

1. **默认 UI 路径走的是旧 AgentPanel**。`readAgentSurface()` 在未配置环境变量时
   返回 `"panel"`，而 `editor-client.tsx` 在非 floating 模式下渲染**旧的
   `AgentPanel`**，它经 AG-UI runtime → `direct-runs` → 旧微服务。
   也就是说：**默认配置下 AI 助手的流量仍走待退役的服务**。
2. **有 4 个可达的旧服务调用点 + 3 个待归档的旧客户端模块**，
   之前只是散在若干笔记里，没有一个可读的余额。

## Decision

新增 `tests/unit/agent-retirement-audit.test.ts`：把能力矩阵做成**棘轮**。

### 1. 断言「恰好等于清单」，而不是「等于零」

当前确实不为零。断言零会立刻失败，然后被人改成 `skip` ——
**那比诚实列出更糟**：一个被跳过的测试会在 CI 里显示为绿色。

断言的是：实际集合 **恰好等于** 已知清单。

- 新增一个调用点 → 失败（必须显式加进清单，也就是「承认欠了一笔债」）；
- 减少一个 → 也失败（必须更新清单，也就是「记录还款」）。

这让「还欠多少」始终是一个**可读的数字**，而不是需要考古的猜测。

### 2. 必须全树扫描，不能只扫清单里的文件

第一版只遍历 `KNOWN_LEGACY_CALL_SITES` 的键。那有个致命缺口：
**有人在「新文件」里写 `createAgentClient()` 时，测试一个都扫不到** ——
棘轮只能发现「已列出的文件里数量变了」，形同虚设。

改为递归扫描 `app/` + `components/` + `lib/` + `hooks/`（跳过 `.next`、
`node_modules`、`tests`）。

**改完全树扫描后立刻发现我手工清单遗漏的 3 个文件** —— 那三个是
`lib/agent/client.ts` / `token.ts` / `direct-run-client.ts`，
即**定义处**而非调用处。这暴露了检测规则的一个问题（见下）。

### 3. 定义处与调用点分开记账

三个 `export function createAgentClient/signAgentToken/fetchDirectAgentRunStream`
是模块**定义处**，不是调用点。两者要归档的动作不同：

- 消除调用点 = 把某条路径切到新实现；
- 删除模块 = 调用点全部消除**之后**才能做的事。

混在一起会让余额不可读（「6 处调用」里其实有 3 处是定义）。
因此拆成两张清单：`KNOWN_LEGACY_CALL_SITES`（4 个文件 / 6 处）
与 `KNOWN_LEGACY_MODULES`（3 个模块）。

### 4. 把「默认走旧面板」这个事实钉进测试

```ts
expect(readAgentSurface({})).toBe("panel");
```

这条断言的价值在于：**它失败的时候正是切流完成的时候**。
届时应当更新它并删除相关断言 —— 而不是让它变成一条没人看的注释。

### 5. 已 Web 化的能力：断言「不引用旧配置键」

plan 要求「未配置 Agent URL/JWT/Redis 仍可使用」。对已 Web 化的路由来说，
可行性的判据是它们**根本不引用** `AGENT_BASE_URL` / `COLLAB_JWT_SECRET` /
`REDIS_URL` 等配置键 —— 引用而不校验会让「未配置」在运行时才暴露。

### 6. 扫描有效性单独断言

若 `listSourceFiles` 因路径写错返回空数组，主断言会因为 `actual = {}` 而失败 ——
但那时失败原因（路径错）与真实语义（没有旧调用了）**难以区分**。
因此单独一条断言把「扫描确实在工作」钉住（文件数 > 100 且包含已知含调用的文件）。

## 实测修正的问题（红 → 绿）

**全树扫描抓到我的手工清单遗漏 3 个文件。** 这本身就是「为什么必须全树扫描」
的最好证明：我逐个人工搜索时把它们当成「定义」忽略了，而它们在
`lib/agent/` 下、同样是待退役的东西。

修正方式不是把它们塞进调用清单，而是**新增一张定义清单** ——
因为归档动作不同。

## Alternatives considered

- **断言旧服务调用点为零** — 最「干净」的目标状态。
  否决原因：当前不为零，断言零会立刻失败。而失败的自然反应是
  `it.skip` 或注释掉 —— 那会制造「CI 绿色但债还在」的假象，
  比诚实列出更危险。棘轮的作用是让余额可见且单调下降。
- **只扫清单里列出的文件**（我第一版的写法）— 更快、失败信息更聚焦。
  否决原因：**在新文件里加调用完全检测不到**，棘轮形同虚设。
  实测证明了这一点：改全树扫描后立刻发现 3 个遗漏文件。
- **用正则匹配整个文件内容而不逐行判断注释** — 实现更短。
  否决原因：润色与 helpers 路由的注释里都提到 `signAgentToken`
  （说明「已完全移除」）。不排除注释会把它们误报成仍在使用 ——
  而那会让审计的可信度直接归零（一个总在说谎的检查会被忽略）。
- **把 definition 与 call 合并成一张「旧代码清单」** — 清单更短。
  否决原因：两者归档动作不同（删调用 vs 删模块），合并后余额数字
  无法回答「还差几步」。分开记账让每张清单都能单独归零。
- **断言 `readAgentSurface({}) === "floating"`**（即先改默认值）—
  更接近目标状态。否决原因：那是**切流动作本身**，需要同时改
  `editor-client` 的分支与浮窗的行为，且需要人工冒烟。
  本提交只做审计；先改默认值会让「切流未完成」这件事被掩盖。

## Consequences

- **收益**：能力矩阵从文档主张变成 CI 约束；余额可读且单调；
  「默认走旧面板」这个关键事实被钉住；已 Web 化能力的「不依赖旧配置」可验证。
- **代价**：多一个扫描类测试（读文件系统，约 16ms）；清单需要人工维护
  （但这正是设计意图 —— 每次还债都必须显式记录）。
- **已知上限**：
  - **棘轮只覆盖 `apps/web`**。`scripts/`、`.github/`、根 `package.json`
    里的旧服务引用（如 `build:agent`、`deploy-agent.yml`）未纳入 ——
    那属于 P07 任务 4/5。
  - **检测规则是符号名匹配**，不做类型分析。若有人把旧调用包一层
    （`const c = createAgentClient; c()`），当前规则仍能命中第一行；
    但更复杂的间接引用（别名导入）可能漏检。
  - **默认 surface 仍是 panel**。因此「默认走旧面板」这条断言目前是
    **绿的**（事实描述），切流后它会变红 —— 那是预期的信号，不是故障。
- **什么信号发生时该重访**：切流（P07 任务 3）时，本测试会因清单减少而
  需要更新 —— 那正是它的设计用途。当两张清单都归零时，
  应当删除审计测试本身，并把「旧服务零引用」作为一条硬断言。

## Verification

- `apps/web/tests/unit/agent-retirement-audit.test.ts`（14 例）：
  - **调用点棘轮**：**全树扫描实际调用点恰好等于清单**、
    清单文件都存在、**已 Web 化路由只有注释提及而无真实调用**；
  - **模块清单**：**恰好三个定义处模块**、三个文件都存在；
  - **默认 UI 路径**：**默认 surface 是 panel（即旧 AgentPanel 路径）**、
    浮窗需显式配置、未知取值保守回落到 panel、
    editor-client 确实有两个 surface 分支；
  - **能力矩阵**：11 个已 Web 化路由**都不含旧服务调用**、
    文件都存在、**都不引用旧配置键**（AGENT_BASE_URL / COLLAB_JWT_SECRET /
    REDIS_URL）；
  - **扫描有效性**：全树文件数 > 100 且包含已知含调用的文件；
  - **余额可读**：未完成调用点数（6）。
- 红 → 绿：全树扫描（第一版只扫清单文件）**立刻发现手工清单遗漏的 3 个文件**，
  暴露出「定义处与调用点未区分」的问题。改为两张清单后 14/14 通过。
- 全量：`pnpm test` 1635 例通过、`typecheck` 四包全绿、
  `lint` 0 error（12 warning = 基线）。

# Agent Note: 服务端写库后，客户端必须同步内容 —— 但绝不能覆盖本地输入

Status: implemented

## Problem

P07 任务 3 要把浮窗切到 `/api/ai/runs`。核实了两条路径的**写入位置**，
发现这是切流最核心的差异 —— 而它不显眼：

| | 旧路径（`/api/agent/floating/chat`） | 新路径（`/api/ai/runs`） |
|---|---|---|
| 谁写库 | **客户端**：组件调 `applyOperation` → 表单变更 → autosave 提交 | **服务端**：`commitToolProposal` → `commitResumeMutation` |
| 留痕 | 依赖 autosave | 提交语句内原子完成 |
| 幂等 / 租约 | 无 | 有 |

也就是说：新路径下服务端**已经写完库了**。客户端若不把自己的表单同步过去，
会有两种后果：

1. 界面显示旧内容 —— 用户要刷新才发现变化；
2. **更糟**：本地稍后的一次 autosave 用旧内容把服务端的修改**覆盖回去**。

### 一个关键事实：回执事件不带内容

`mutation.committed` 的 payload 只有 `{ mutationId, revision, changeSetId }`。

这是**有意**的（事件流不该承载整份简历快照），但意味着客户端**必须另外取内容**。
本模块的输入因此是「回执 + 另取的内容」：回执给 `revision`（CAS 基准），
内容由调用方用 `getResumeMutationBaseline(resumeId)` 取。

## Decision

新增 `lib/ai-client/commit-sync.ts`：纯函数，`回执 + 内容 + 本地是否有编辑 → 同步方案`。

### 1. 有本地编辑时**只推进基准，不覆盖表单**

这是防数据丢失的核心。用户可能正在输入 —— 把服务端内容直接写进表单会
**抹掉他刚敲的字**。

正确做法是只推进基准，让本地那次提交带着新基准去提交；
若目标字段真的被服务端改过，服务端的 CAS 会如实返回冲突，
走既有的冲突 UI（P02/P03 已交付）。

### 2. 回执缺 `revision` 时不猜

`useResumeMutationSession` 的基准推进是**乐观**的（本地提交后自己 +1）。
新路径下服务端可能因并发落在别的 revision 上（它有自己的 CAS）。

用本地推断的值去同步，会让后续提交的 `expectedRevision` 与真实值错位 ——
表现为「**明明没冲突却报冲突**」，而那类故障极难定位
（错误信息说冲突，但用户确实没改过）。

因此缺 revision 时返回 `reload`，让调用方重拉 baseline。

### 3. 两个 `reload` 原因分开

- `missing-revision`：回执本身不可用 —— **契约违例**，应当上报；
- `missing-content`：内容取不到（网络/越权）—— **可重试的失败**。

合成一个码会让调用方无法决定「提示重试」还是「报错」。
（我第一版就是合在一起的，写测试时发现语义不清。）

### 4. 多次提交只取**最后一次** revision

一次 Run 可能提交多次（多个工具各自提交）。中间态的 revision 已经过时 ——
用它推进基准会让本地落后于服务端。

**这一点有个具体的失败场景**：先提交在 rev 3、再提交在 rev 5，
若用 rev 3 推进基准，本地会以为自己落后 1 个版本，
而实际服务端已在 rev 5 上 —— 下一次本地提交会被 CAS 拒绝（`condition_mismatch`）。

### 5. 缺内容不阻塞基准推进

有本地编辑时即使取不到内容，仍返回 `advance-baseline-only`。
否则本地后续提交会一直用旧基准 —— 而基准推进**不需要**内容。

## Alternatives considered

- **由服务端在 `mutation.committed` 事件里带上完整内容** — 客户端不用另取。
  否决原因：事件会逐条落库，带上整份简历快照会让事件表体积急剧膨胀
  （每次提交都存一份完整 JSON）。且事件流是**增量**语义，
  塞进全量快照会让「续读」的语义混乱。当前设计（回执只给 revision，
  内容另取）职责更清楚。
- **客户端直接从事件流累积内容**（把 `tool.succeeded` 的参数拼起来）—
  不用额外请求。否决原因：那等于在客户端重新实现一遍提交语义
  （条件校验、字段白名单），而服务端已经做完并原子落盘了。
  客户端的推算一旦与服务端不同，就会出现「界面与服务端不一致」——
  而这正是本模块要防的。
- **无条件把服务端内容写进表单**（不判断本地编辑）— 实现最简单。
  否决原因：会抹掉用户正在输入的内容。这是不可接受的数据丢失 ——
  且它发生在「用户刚敲完字、AI 同时提交」这个相当常见的时序下。
- **无条件不写表单，只推进基准** — 更保守，绝不丢数据。
  否决原因：那界面就永远显示旧内容，用户要刷新才看到 AI 的改动。
  本模块的价值正是在这两种极端之间给出**有条件的**决策。
- **缺 revision 时用本地基准 +1 推断** — 让流程能走下去。
  否决原因：见上，服务端有自己的 CAS，本地推断必然在某些时序下错位，
  而产生「假冲突」这种极难排查的症状。
- **两个 reload 原因合成一个码** — 类型更简单。
  否决原因：调用方需要区分「重试」与「上报」。我第一版合在一起，
  写测试时发现断言无法表达这个区别。

## Consequences

- **收益**：切流的最后一环（服务端写库 → 客户端同步）有了明确且可测的决策逻辑；
  两条数据丢失路径（覆盖本地输入、用旧基准提交）都被显式拦住。
- **代价**：多一个模块（约 120 行 + 12 例测试）；调用方需要在收到回执后
  额外发一次 `getResumeMutationBaseline`。
- **已知上限**：
  - **尚未接入浮窗**。本模块提供决策，但 `floating-agent-chat.tsx`
    仍走旧路径。切流需要改那个 2511 行组件（替换 fetch 目标、
    在 `committed` 动作上调用本模块、翻转默认 surface）
    且需人工冒烟（浮窗/停靠、移动端、暗色）。
  - **未处理「同步过程中又有新提交」**。若在取内容期间服务端又提交了一次
    （罕见但可能，例如两个工具并发），当前实现会用较旧的 revision 推进基准。
    事件流的 sequence 单调性让这类窗口很小，但严格来说需要按 revision 比较
    （取更大的那个）才完全正确。
  - **`serverContent` 的类型是 `ResumeContent`**，但读取层返回 `unknown`
    （`getResumeMutationBaseline` 的签名）。调用方需要走 `migrateContent`
    + `ResumeContent.parse` —— 那一步不在本模块里（它不该承担解析职责）。
- **什么信号发生时该重访**：切流后若用户反馈「AI 改完后界面没变」，
  先查是否漏调本模块（服务端写库但客户端没同步）。
  若反馈「我打了一半字，AI 一改就没了」，检查 `hasLocalEdits` 的判据
  是否真的反映了 dirty 状态（`mutationSession` 的 `dirtyRef`）。

## Verification

- `apps/web/tests/unit/ai-commit-sync.test.ts`（12 例）：
  - **同步决策**：无本地编辑 + 有内容 → sync（revision 来自回执而非本地推断）、
    **有本地编辑 → 只推进基准不覆盖表单**（且不带 content）、
    **回执缺 revision → reload(missing-revision)**（4 种非法值）、
    **取不到内容 → reload(missing-content)**（与契约违例区分）、
    **有本地编辑时即使取不到内容也推进基准**；
  - **多次提交**：**取最大 revision**、忽略非 committed、忽略缺 revision、
    无回执返回 null、单次提交；
  - **诚实性**：reload 分支不带 content（避免调用方误用空内容）、
    只有 sync 分支返回内容。
- 全量：`pnpm test` 1652 例通过、`typecheck` 四包全绿、
  `lint` 0 error（12 warning = 基线）。

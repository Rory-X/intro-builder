# Agent Note: Continue 路由 —— 继续执行比启动多三类危险

Status: implemented

## Problem

`POST /api/ai/runs/[runId]/continue` 恢复一个等待中或中断的 Run。它与启动路由
形状相似，但危险性更高：它是在**已有 Run 上再跑一次**。落地时守住的三条边界，
每条都对应一类会静默破坏不变量的缺陷：

1. **接管仍然有效的租约**。若另一个请求正在执行时被接管，同一个 Run 会出现两个
   attempt 并发写同一份文档 —— 两份事件交错、`sequence` 混乱、同一个
   `toolCallId` 可能被提交两次（幂等键相同但并发到达时服务端只能串行处理一个）。
2. **对终态 Run 继续**。「终态只出现一次」是 Run 状态机的核心不变量；
   继续一个已完成的 Run 会让它失效，用户会看到同一个任务「又活了一次」。
3. **基于过期检查点继续**。客户端带着旧的 `checkpointVersion` 提交回答时，
   它引用的问题可能已经不存在（期间 Run 已推进）。把回答挂到错误的位置上，
   用户会看到「我明明回答了，它却问别的」。

另有一条归属要求：他人的 Run 不能继续，且不能泄露它是否存在。

## Decision

### 1. 拿不到租约一律 409，不做「尽力而为」的接管

`acquireLease` 的条件 UPDATE 只在「Run 非终态、且当前无有效租约（或已过期）」
时成功。因此这一条 SQL 同时解决两个方向：

- **有人正在执行** → `held_by_other` → 409。「接管」在这里是错的：它不会让
  执行更快，只会让两个 attempt 同时写同一份文档。
- **上一个持有者被平台硬杀、租约已过期** → 成功。这正是可恢复路径 ——
  租约过期是「进程确实死了」的唯一可靠信号（AbortSignal 在硬杀时不会触发）。

### 2. 终态检查与检查点版本都比在副作用之前

顺序固定为：**鉴权 → 读 Run → 归属校验 → 终态检查 → 请求体形状 →
检查点版本比对 → provider 校验 → 读简历 → 申请租约 → 执行**。

检查点版本刻意放在申请租约**之前**：版本不符是客户端可恢复的状态
（刷新后重试即可），没必要为它白占一次租约 —— 租约会短暂阻塞其它合法请求。

`waiting_user` 与 `interrupted` **不是**终态，两者正是本路由存在的理由。

### 3. 授权模式取自已落库的 Run 行

`writeMode` 从 `getRun()` 读，**不**取自请求体。若客户端能自选，就等于可以
单方面把审批模式降级成直接写入 —— 那是授权语义，必须由服务端状态决定。

### 4. 历史从已持久化事件重建，且不重放工具

`buildHistoryFromEvents` 只取用户可见的问答对（`text.delta` 累积的助手文本，
按结束类事件收成一条消息）。**不**重放工具调用：已提交的操作应按回执查询
（`GET` 路由已有工具账本），重放会让「继续」变成第二次修改。

### 5. 共享执行流

推流、fence 透传、终态落库、租约释放全部在 `lib/ai/run-route-support.ts`，
启动与继续两条路由共用。这几段若各写一遍，迟早出现「一条修了、另一条没修」的
漂移 —— 而每条错误都涉及取消与租约这类难排查的故障。

收尾顺序在共享实现里明确为：**先写终态、再释放租约、最后关流**。
反过来（先释放租约）会留出一个窗口：Run 还是 `running` 但租约已空，
此时另一个请求可以拿到租约并开始执行 —— 同一个 Run 出现两个 attempt。

## Alternatives considered

- **拿不到租约时接管（强制换持有者）** — 能让「用户点了继续但没反应」立刻变成
  「继续了」。否决原因：这会让两个 attempt 并发写同一份文档。硬杀后的恢复
  已经由「租约过期」覆盖，真正的并发执行不该被抢占。
- **允许对终态 Run 继续（把它当作「再来一轮」）** — 实现最省事，
  且符合一部分用户直觉。否决原因：终态只出现一次是 Run 状态机与 `finishRun`
  的基础（0 行 = 已终态）。放开它需要重新设计终态语义，属于另一个特性，
  不该在「恢复」这个切片里顺手改。若确实需要「再来一轮」，应当**新建一个 Run**。
- **从请求体读 `writeMode`** — 与启动路由的参数形状一致，客户端更省事。
  否决原因：那是授权语义。请求体是客户端可控输入，允许它自选等于允许
  单方面把「需要用户批准」降级为「直接写入」。
- **恢复时重放之前的工具调用**，让模型看到完整执行轨迹 — 上下文最完整。
  否决原因：写工具会产生**真实提交**，重放就是第二次修改。已提交的操作
  应当按回执查询。这也与 P02 的幂等设计冲突：同一 `mutationId` 同 payload
  会返回原回执（不会二次写入），但重放中若 ID 被重新生成就会变成新修改。
- **检查点版本不符时直接按最新版本继续** — 用户少一次刷新。否决原因：
  客户端提交的回答是针对某个具体问题的；挂在未知版本上会让用户看到
  「我回答的问题不见了」。409 + 当前版本号让前端能提示「已更新，请刷新」。
- **不拆分共享模块，两条路由各写一遍** — 少一层间接。否决原因：
  重复的这几段每一条都涉及难排查的故障（取消后仍写库、租约不释放阻塞请求），
  而重复代码必然漂移。

## Consequences

- **收益**：等待中与中断的 Run 都能恢复；并发接管被结构性拒绝；
  终态不变量保持；过期检查点不会让回答错位；两条路由的执行语义完全一致。
- **代价**：多一层 `run-route-support.ts` 间接；历史重建刻意很薄，
  模型在继续时**看不到**之前的工具调用细节（它只能看到问答文本）。
  这是有意的取舍：读工具账本比重放安全，但目前没把账本喂给模型。
- **已知上限**：
  - `buildHistoryFromEvents` 是启发式的：它按「结束类事件」切分助手消息。
    若一次 attempt 产生多段 `text.delta` 由不同结束事件隔开，会被切成多条消息，
    顺序正确但粒度可能与原始对话不完全一致。
  - 继续时**不校验** `resumeId` 是否与 Run 上记录的相同 —— 它直接用
    Run 行的 `resumeId`（这是正确的来源），因此客户端无法换一份简历继续。
  - `requestId` 在本路由只做格式校验，未用于幂等复用（启动路由用它复用 Run）。
    重复的 continue 请求会各自申请租约，后者因租约被占而 409。
- **什么信号发生时该重访**：若用户报告「继续之后模型忘了前面说过什么」，
  说明历史重建太薄，应把工具账本（`listToolExecutions`）也纳入上下文。
  若出现「同一个 Run 有两个 attempt 在跑」，先查租约时长 `LEASE_TTL_MS`
  是否小于实际执行时间 —— 那会让合法执行中途被抢。

# Agent Note: 任务卡投影 —— 不虚构进度、完成与保存分离、重放幂等

Status: implemented

## Problem

P06 任务 2 要求「从服务器事件生成当前步骤、完成项、等待原因；**没有事件不虚构进度
或百分比**。**模型完成和修改保存分开**。长任务可以折叠，用户滚走时不强制拉回底部」。

前两条是行为约束，每一条都对应一类会让用户误判的 UI 行为：

1. **虚构进度**。最省事的做法是显示「正在处理…」或一个百分比 ——
   但那两者都无法从事件推出。用户据此以为有进度在推进，
   而实际上可能卡在第一步。编一句话比不显示更糟。
2. **把「模型完成」显示成「已保存」**。这是「模型完成 ≠ 已保存」在 UI 层的落点。
   模型可以说完话而什么都没写（诊断类任务），也可以写了东西但连接在收尾前断掉。
   把两者混成一个状态，用户会在刷新后发现内容没变。

## Decision

新增 `lib/ai-client/task-projection.ts`，纯函数：`事件数组 → 任务卡`。

与既有 `ai-client/reducer.ts` 是**消费者与被消费者**关系：reducer 产出完整的
机器投影（工具、提案、决策、冲突…），本模块把它收敛成一张卡需要的字段。
两者关注点不同，因此不是重复实现。

### 1. 没有事件就不虚构

- `taskCardHeadline` 在 `running` 且**没有任何步骤**时返回 `null`，
  让 UI 保持沉默，而不是显示「正在处理」。
- 不提供百分比字段。事件里没有进度信息，编一个出来是欺骗。
- `idle` 不显示任何标题。

### 2. 完成与保存是两个独立事实

`TaskCard` 有两个独立字段：

- `status`：面向用户的整体状态（`done` / `interrupted` / …），由终态事件决定；
- `hasPersistedChanges`：**唯一**依据是 `mutation.committed` 事件是否存在。

文案据此区分「已完成」与「已完成并保存」。`shouldShowSavedBadge` 单独成函数，
因为它很容易被写成 `status === "done"` —— 而那会把「模型说完但没写」
显示成「已保存」。

**有回执但连接中断时，`hasPersistedChanges` 仍为 `true`**：
落盘是已发生的事实，不该因断线而撤销。UI 需要两个字段一起看
（「已保存，但连接中断」）。

### 3. 等待原因是可操作的

`run.waiting_user` 带出问题文本；缺少文本时 `pendingQuestion` 为 `null`
（不编一个问题），但概览退化为「等待你的确认」—— 仍不撒谎。

### 4. 面向用户的语言，不是内部命名

- 工具名映射成业务动作（`updateProjectBlock` → 「更新项目经历」）。
  未知工具给兜底「执行一项操作」，**不回显原始工具名**。
- 错误码映射成可操作说明（`target_not_found` → 「找不到这条内容，可能已被删除」）。
  未识别的码给「这一步没有完成」，**不显示原始码**。
- 测试专门断言序列化后的任务卡不含 `apiKey` / payload / 原始参数。

### 5. 终态收尾：不留转圈的步骤

Run 进入 `failed` / `interrupted` / `cancelled` 时，仍在 `running` 的步骤
标为 `failed` 并给「未完成」/「已取消」。不处理的话，一个被中断的 Run 会
永远显示「正在更新项目经历…」，而那个工具再也不会返回。

## 实测发现并修复的缺陷（红 → 绿）

**重放会让步骤重复显示**。第一版对 `tool.started` 直接 `push`，
于是同一批事件重放两次会产生两条相同步骤。

这条被测试抓到（`expected [ …(2) ] to have a length of 1 but got 2`），
而它违反的正是任务 6 的「重放 event 不重复 toast/写入」——
我把那条要求归给了 reducer，却忘了任务卡是**独立投影**，同样需要幂等。

修法：按 `toolCallId` / `mutationId` / `changeSetId` **去重**。

刻意不采用「覆盖同一索引」的写法：那会保留第二条而丢掉第一条的位置，
步骤顺序会与真实发生顺序不符。去重保留了首次出现的位置。

提交事件的去重比工具更重要 —— 重放若产生两条「已保存修改」，
用户会以为做了两次改动，而实际只有一条回执。

## Alternatives considered

- **复用 `reducer.ts` 的 `RunProjection` 直接渲染** — 不新增模块，少一层。
  否决原因：reducer 的投影服务于「重建完整运行状态」（含 seenEventIds、
  sequence、原始 payload），而任务卡需要的是「给用户看的三五行」。
  两者目标不同：把 UI 文案逻辑塞进 reducer 会让那个已被多处使用的模块
  承担展示职责。
- **显示进度百分比** — 用户更安心。否决原因：事件里**没有**进度信息。
  要算百分比就得猜总步数，而模型可能调 1 个工具也可能调 8 个。
  猜出来的百分比是假的，用户会据此判断「快好了」而实际刚到第一步。
- **用 `status === "done"` 作为「已保存」的依据** — 一个字段就够。
  否决原因：那正是本任务要防的错误。模型可以说完话而没写任何东西。
  分成两个字段后，UI 被迫分别展示，这个约束就在类型上成立了。
- **失败时显示原始错误码**（便于用户反馈问题）— 排查更方便。
  否决原因：用户拿 `target_not_found` 做不了任何事。
  「找不到这条内容，可能已被删除」才是可操作的。需要原始码的场景是
  开发排查，那有日志与 tool ledger，不必占任务卡的篇幅。
- **中断时把未完成步骤标为 `done`**（避免显示失败）— 界面更「好看」。
  否决原因：那是谎报。用户会以为工具执行完了，而实际结果不存在。
  `failed` + 「未完成」如实反映了「这次没跑完，可以重试」。
- **重放时用「覆盖同一索引」保持步骤数不变** — 我第一版考虑的写法。
  否决原因：它保留第二条、丢掉第一条的位置，步骤顺序与真实发生顺序不符。
  去重（跳过重复）保留首次位置，语义正确。

## Consequences

- **收益**：任务卡不会虚构进度；「完成」与「保存」在类型层面分开；
  等待原因可操作；内部命名与凭据不泄漏；重放幂等。
- **代价**：多一层投影（reducer → 任务卡），且工具名/错误码各维护一份
  中文映射表 —— 新增工具时必须同步加标签，否则用户看到兜底文案。
- **已知上限**：
  - **未接线到 UI**。本模块只提供计算，`floating-agent-chat.tsx` 尚未使用它。
    那需要与任务 3（changeSet 卡）一起做，属后续工作。
  - plan 要求「长任务可以折叠，用户滚走时不强制拉回底部」——
    这两条是**渲染行为**，本模块只提供 `steps` 数组，折叠与滚动策略由组件实现。
  - 工具名映射表是手写的。若新增工具忘记加标签，用户会看到「执行一项操作」
    （不算错，但信息量低）。没有机械检查能发现「忘了加」——
    除非把 `REQUIRED_TOOL_NAMES` 与映射表做完整性比对，那是可做的改进。
- **什么信号发生时该重访**：若用户反馈「任务卡上的步骤看不懂」，
  检查是否有工具走了兜底文案（说明映射表漏了）。若要做上面那条完整性检查，
  在 `task-projection` 里引入 `REQUIRED_TOOL_NAMES` 并断言映射表覆盖它。

## Verification

- `apps/web/tests/unit/ai-task-projection.test.ts`（28 例）：
  - **不虚构**：空事件 → idle；无步骤时不显示「正在处理」；
    `emptyTaskCard` 与空事件投影一致；
  - **业务语言**：工具名映射、未知工具兜底且**不回显原始名**、
    成功 → done、失败 detail 是可操作中文且**不含原始码**、未识别码有兜底；
  - **完成 ≠ 保存**：只有 `run.completed` → 「已完成」且 `hasPersistedChanges`
    为 false；有回执 → 「已完成并保存」；提交步骤带版本号；
    **有回执但中断 → 仍为已保存**；
  - **等待**：带出问题文本、askUser 步骤标 waiting、
    缺文本时 `pendingQuestion` 为 null 且概览不撒谎；
  - **提案**：就绪 → waiting 且不算保存；
  - **终态收尾**：中断/取消时未完成步骤被标注、完成状态不改动提案步骤、失败概览；
  - **冲突计数**；
  - **纯函数性质**：重复投影结果相同、**重放不产生重复步骤**、不改动入参；
  - **不泄漏**：序列化后不含 apiKey / payload / 原始参数。
- 红 → 绿：28 例中 1 例一开始失败（重放去重），暴露了「任务卡作为独立投影
  也需要幂等」这一被我遗漏的要求。修正后 28/28 通过。
- 全量：`pnpm test` 1376 例通过、`typecheck` 四包全绿、
  `lint` 0 error（12 warning = 基线）。

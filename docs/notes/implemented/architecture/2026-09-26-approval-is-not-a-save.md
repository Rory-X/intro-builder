# Agent Note: 批准不等于已保存 —— change-set 决策路由的两条区分

Status: implemented

## Problem

请求批准模式下，AI 的修改先落成一个 change-set（提案），用户点「应用」才写文档。
这条路径上有两个非常容易做错、且错了不会被现有测试发现的点：

1. **陈旧版本被静默接受**。AI 可以在这期间重新生成提案（proposalVersion 递增）。
   用户看到的是第 2 版，点「应用」时库里已经是第 3 版。若不做版本比对，
   这次批准会挂在一份已经不存在的内容上 —— 用户以为应用了自己看过的改动，
   实际应用的是他没看过的。
2. **把「批准」当成「已保存」**。批准发生在文档提交**之前**。若提交遇到
   revision 冲突（用户在别处改了同一段），文档根本没变。此时若响应
   `applied: true`，UI 会显示「已应用」，而用户刷新后发现改动不见了 ——
   这正是 P02/P03 反复修掉的同一类「假成功」，换到了审批路径上。

此外还有归属问题：他人的 changeSet 不能决策，且**不能泄露它是否存在**。

## Decision

决策路由（`app/api/ai/change-sets/[changeSetId]/decisions/route.ts`）用四条机械规则守住边界：

1. **版本精确匹配**。`validateDecision` 比对 `proposalVersion`，不符返回 **409**
   （不是 400，那是格式错误；不是 500，那不是服务端故障），且在版本校验通过
   **之前不写任何决策记录** —— 「不产生落盘副作用」是这里的关键，否则批准会
   已经挂在旧版本上，再返回 409 也晚了。
2. **决策与提交分离，且顺序固定**。先 `recordDecision` 写批准记录；**记录没落库
   就绝不继续提交**，否则会出现「文档被改但没有任何批准记录」，事后无法解释
   这次修改是谁、基于哪一版批准的。记录失败返回 409。
3. **`applied` 只认真实回执**。响应里的 `applied` 仅在
   `commitResumeMutation` 返回 `status === "committed"`（含 `mutationId` +
   `revision`）时为 `true`。提交冲突时状态是 `awaiting_commit`
   （「已确认，尚未保存」），`applied: false`。
4. **冲突不标终态**。冲突时提案**保持** `pending` 而不是标成 `committed`：
   用户修正冲突后还应能再次应用同一提案；提前标终态会让提案永久无法重试。

归属校验一律返回 **404**（不存在与不属于当前用户不可区分），403 会泄露
`changeSetId` 的存在性 —— 与 `api/ai/runs/[runId]` 的处理保持一致。

全部拒绝是**终态而非失败**：写决策 + 把提案标为 `rejected`，不调用提交，
返回 `applied: false` 且不产生任何文档变更。

## Alternatives considered

- **批准时直接提交，不单独存决策记录** — 代码更短，少一张表的读写。否决原因：
  提案的 `changeSetVersion` 正是「这份批准针对哪一版内容」的唯一凭据。
  不存它，「先批准 v1、AI 改成 v2、再应用」这条路径无法被审计，也无法判断
  一次文档修改的依据是什么。P04 契约明确要求批准绑定 operation IDs + proposalVersion。
- **版本不符时返回 400 而不是 409** — 客户端实现更省事（只判 4xx）。否决原因：
  这两种情况对客户端**含义完全不同**。400 表示「你构造的请求有错，改了才能重试」；
  409 表示「请求没错，但服务端状态变了，你需要重新读取再决定」。
  前端据此决定是提示「参数错误」还是「内容已更新，请重新确认」。
- **提交冲突时把提案标为 `committed`，让用户手动再点一次** — 否决原因：
  这等于对用户谎报（他并没有得到已保存的东西），且会把提案推入终态。
  保留 `pending` 才能让「再次应用」成为可能。
- **先提交、成功后再写决策记录** — 表面更「高效」（少一次失败路径）。
  否决原因：一旦决策写入失败，文档已经改了但没有批准依据，比拒绝整次请求严重得多。
  顺序必须是「先留痕，后改文档」。
- **在请求体里接受 `userId` 以支持服务端到服务端调用** — 否决原因：
  那会让鉴权退化成「调用方自称身份」。归属只能来自会话。

## Consequences

- **收益**：审批路径上的两种「假成功」被封死 —— 陈旧批准无法生效，
  冲突不会被报成已应用。`applied` 字段的含义收紧为「文档真的落盘了且拿到回执」，
  前端可以安全地用它驱动「已保存」提示。
- **代价**：一次成功的应用需要两次写（决策 + 提交），且版本不匹配时用户必须
  重新确认，多一个来回。这是有意买的正确性。
- **已知上限**：本路由**不检查** Run 是否仍可写。带 `fence` 的提交保护在
  `commitResumeMutation` 的 CTE 内实现，但本路由构造 principal 时**没有**填入
  `fence` —— 因为用户的显式批准发生在 Run 结束之后，此时租约通常已释放，
  强制要求 fence 会让正常的「批准已结束的 Run 的提案」全部失败。
  这意味着：**取消一个 Run 不会阻止用户随后批准它遗留的提案**。
  这是当前有意的取舍（用户显式点击批准，理应生效），但它与「取消拦住晚到提交」
  的语义在边界上不同，需要时可在此处补一条显式规则。
- **什么信号发生时该重访**：若用户报告「取消了任务但提案仍能应用」并认为这是缺陷，
  就在本路由的 principal 上加 fence 校验（并在 Run 终态时决定是否仍接受批准）。

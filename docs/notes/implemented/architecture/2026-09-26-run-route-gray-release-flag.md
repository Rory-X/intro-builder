# Agent Note: 新执行链路的灰度开关默认关闭

Status: implemented

## Problem

`/api/ai/runs/*`（启动与 continue）是**服务端可达**的执行入口：任何人知道 URL
就能 `POST` 触发一次模型执行。而在 P04 落地时它有两个未完成的前提：

- 客户端浮窗尚未接过来（`floating-agent-chat.tsx` 仍打 `/api/agent/floating/chat`）；
- 从未做过真实浏览器冒烟。

没有开关时，「代码合并」就等于「生产立即可达」。一旦新链路有问题（例如某个工具的
提案形状不对、或租约在真实并发下表现不同），影响面是**全部用户**，
而且排查时会发现有两个执行入口同时在跑，难以判断是哪一条出的错。

plan 因此明确要求「服务端开关默认 **legacy**」。

## Decision

新增 `lib/ai/run-route-flag.ts`，把灰度决策做成**纯函数**（接收 env 对象、
返回决策 + 人类可读理由），与 `scripts/migrate-on-deploy.ts` 的
`shouldRunDeployMigrations` 保持同一范式。两条路由（启动与 continue）共用同一个判定。

判定顺序：

1. **`NODE_ENV=test` 恒开**。否则路由测试会被自己的开关挡住，
   测到的是「503 被拒」而不是真实行为 —— 那等于用开关买到一个没有意义的绿灯。
2. **显式 `AI_RUN_ROUTE_ENABLED`** 优先。接受 `1`/`true`/`yes`（大小写不敏感、
   允许空白）开启，`0`/`false`/`no` 关闭。
3. **其余一律关闭**，包括空字符串与未设置。

关键取舍：**无法识别的取值按关闭处理**。`maybe`、`on`、`2` 这类拼写不会打开
一条未验证的执行路径。反过来（把未知值当作开启）会让一个拼错的开关名
意外放行全部生产流量。

关闭时返回 **503** 而非 404，并带 `code: "run_route_disabled"` 与理由。
404 会让调用方以为「路由不存在」而去猜路径；503 明确表达「有意关闭」，
理由让运维能区分「没开」与「配错了」。

开关检查放在**鉴权之前**：关闭时无需读会话，也不该让越权者从响应差异
（401 vs 503）推断「这个路由存在、只是没开」。

## Alternatives considered

- **默认开启，出问题再关** — 少一步配置，新链路能立刻被内部试用。
  否决原因：这条路径尚未冒烟，而它是写文档的（直接模式下会真实提交）。
  「默认开启」把风险敞口设为最大，且回滚需要改配置 + 重新部署；
  「默认关闭」只是晚一点上线，代价小得多，且打开是显式的、可审计的。
- **两套执行链路的开关分开**（启动一个、continue 一个） — 更细粒度，
  例如可以只放 continue 给内部测试。否决原因：只关启动而放开 continue，
  调用方仍能对已存在的 Run 继续执行 —— 开关形同虚设。两条路由共用同一判定，
  这个不变量的测试专门锁住（`ai-run-route-gate.test.ts`）。
- **用 `VERCEL_ENV` 判断环境**（生产关闭、预览开启） — 不需要新环境变量。
  否决原因：`VERCEL_ENV` 表达的是「部署到哪个环境」，不是「这条链路是否启用」。
  两者会被混淆：某天想在预览环境验证旧链路时，会发现开关不受自己控制。
  显式命名的开关让意图写在配置里。
- **把开关做进数据库配置表**（运行时可改，无需重新部署） — 运营更灵活。
  否决原因：这是一个**上线前的安全闸门**，不是运营旋钮。环境变量在部署时确定、
  在代码评审里可见、且天然有审计轨迹；数据库配置会被谁在什么时候改过
  难以追溯，而它控制的是「代码能否执行」。
- **未知取值按「保持默认（关闭）」但不报错** — 与最终选择相同的结果。
  否决原因：结果一样，但**理由的可读性**不同。最终实现把「无法识别」
  写进 `reason` 字符串，让运维一眼看出是拼错了而不是忘了配 ——
  这两者的排查方向完全不同。

## Consequences

- **收益**：新链路默认不可达，合并不会立刻影响用户；打开是显式的、写在
  环境变量里、可审计；两条路由的启用状态不可能不一致。
- **代价**：上线新链路需要一次额外的配置步骤（设 `AI_RUN_ROUTE_ENABLED=1`）
  与重新部署。这是有意买的摩擦力。
- **已知上限**：
  - 开关是**全量**的，没有按用户/会话的百分比灰度。plan 任务 8 提到的
    「指定预览环境先跑新链路」目前靠部署到预览环境 + 该环境设开关来实现，
    而不是同一环境内的部分灰度。
  - 关闭时**没有**把请求转发给旧链路。调用方（客户端）需要自己决定打哪条路由 ——
    当前客户端仍打旧路由，所以这一点不影响现状，但若未来有调用方同时打两条，
    它必须自己处理 503。
  - continue 路由的 `requestId` 仍未用于 attempt 级幂等（schema 无该列），
    这与本开关无关，是另一处已知缺口。
- **什么信号发生时该重访**：当需要「同一环境内只放 10% 流量给新链路」时，
  应把纯函数扩展为接收用户标识并返回稳定哈希判定（而不是引入运行时可变配置）。
  若未来客户端改为打新路由，需要同时处理 503 分支（回退旧链路或提示用户）。

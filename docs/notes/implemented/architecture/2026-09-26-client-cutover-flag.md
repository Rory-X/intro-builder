# Agent Note: 客户端切流开关 —— 唯一危险的组合是「客户端开、服务端关」

Status: implemented

## Problem

P07 任务 3 要把浮窗切到 `/api/ai/runs`。核实后发现一个**不显然但决定部署安全**的问题：

服务端侧已有 `AI_RUN_ROUTE_ENABLED`（`lib/ai/run-route-flag.ts`），
它决定 `/api/ai/runs` 是否可执行。但它是**服务端私有**变量 —— 浏览器读不到。

因此浮窗**无法据此决定**走新路径还是旧路径。没有客户端开关时只有两条路：

- **一次性硬切**（所有用户立即切换）—— 风险最高，一旦新链路有问题影响全部用户；
- **客户端盲试新路径、靠 503 回退** —— 多一次失败请求，且用户会看到界面闪烁。

## Decision

新增 `lib/ai-client/run-path-flag.ts`（16 例测试），与 `resolveRunRouteDecision`
同一判定风格：显式 `NEXT_PUBLIC_AI_RUN_PATH=new` 才走新路径，其余一律旧路径。

### 1. 四种开关组合里只有一种危险

| 客户端 | 服务端 | 结果 |
|---|---|---|
| on | on | 正常走新路径 |
| off | on | 走旧路径（新路径闲置） |
| **on** | **off** | **请求 503** ← 唯一危险 |
| off | off | 走旧路径 |

因此部署顺序必须是**先开服务端、再开客户端**；关闭时顺序相反。
这条约束不显然，所以：

- `isSwitchCombinationSafe` 把它变成**可调用的自检**（返回值里直接写正确顺序）；
- 测试**穷举四种组合**并断言只有一种不安全。

### 2. 无法识别的取值按旧路径处理

与 `resolveRunRouteDecision` 同一理由：拼错的开关名不该意外打开一条未验证的
执行路径。在客户端还有额外后果 —— 客户端以为新路径可用、服务端却没开，
请求会拿到 503。

### 3. 测试环境**不**恒开（与服务端开关刻意不同）

服务端开关在测试环境恒开 —— 因为路由测试直接调 `POST`，若被开关挡住就测不到
真实行为，那等于「用一个开关让测试失去意义」。

**客户端开关不这样做**：测试环境也默认旧路径。理由是两者的测试对象不同：

- 路由测试的对象是**一条路由**，它只有一个「开启」的正确状态；
- 组件测试的对象是**一个组件**，它需要在**两条路径上都能被测**。

> 我第一版抄了服务端那套「测试环境恒开」，**这是一个设计错误**：
> 若测试环境恒开新路径，既有那批 mock 旧路径的组件测试
> （`agent-panel-assistant-ui.test.tsx`，**26 处**旧路由 mock）会全部走新路径
> 而失败 —— 而那批测试正是用来守护旧路径行为的。

因此新路径的组件测试必须**显式**设置 `NEXT_PUBLIC_AI_RUN_PATH=new`
（或直接注入 env 对象）。两条路径的覆盖都是**主动选择**，
而不是被一个「恒开」的默认值悄悄决定。

### 4. `NEXT_PUBLIC_*` 必须静态访问

`readClientEnv` 写成 `process.env.NEXT_PUBLIC_AI_RUN_PATH`（静态属性访问）
而不是 `process.env[name]`。

这是 Next.js 的真实陷阱：`NEXT_PUBLIC_*` 在**构建期**被替换为字面量，
动态取值在服务端能读到、在浏览器里**永远拿到 undefined，且不报错**。

## Alternatives considered

- **不用客户端开关，一次性硬切** — 部署最简单（只改代码）。
  否决原因：新链路从未在真实浏览器冒烟过。一次性切换意味着「一旦有问题，
  影响面是全部用户」，而这正是服务端开关当初默认关闭的理由；
  只在服务端加开关、客户端硬切，等于把那个保护绕过去了。
- **客户端盲试新路径，503 时回退旧路径** — 不需要新开关。
  否决原因：每次切流期间的首次请求都会失败一次（用户看到闪烁或延迟），
  且「回退」需要额外状态（记住已回退），否则每次请求都要重试一遍。
  一个环境变量比这套回退逻辑简单得多，也更可预测。
- **复用服务端已有的 `AI_RUN_ROUTE_ENABLED`**（不加 `NEXT_PUBLIC_`）—
  少一个变量。否决原因：**非 `NEXT_PUBLIC_` 前缀的变量在客户端构建里
  不存在**。浏览器会拿到 undefined，于是永远走旧路径 —— 而表面上「配了开关」，
  排查时极易误判为「开关没生效」。
- **客户端开关默认 `new`**（新路径优先）— 更「先进」。
  否决原因：与服务端开关同一逻辑 —— 未验证的路径不该是默认。
  且默认 `new` 会让「忘记配置」变成 503（客户端开、服务端关）。
- **`isSwitchCombinationSafe` 只返回布尔值** — 更简洁。
  否决原因：返回 `reason` 让调用方（部署自检脚本或日志）能**直接输出
  正确顺序**，而不是只告诉运维「不安全」然后让他去查文档。
- **把开关逻辑放进组件** — 少一个模块。否决原因：那是 2511 行组件里
  最难测的一处，而四种组合 + 三种非法取值必须穷举。

## Consequences

- **收益**：切流可以**分两步安全部署**（先服务端、再客户端）；
  危险组合有可调用的自检与穷举测试；Next.js 的 `NEXT_PUBLIC_*` 陷阱被显式处理。
- **代价**：多一个环境变量与一个模块（约 130 行 + 16 例测试）。
  部署流程多一条顺序约束（但它是**必须**有的）。
- **已知上限**：
  - **浮窗尚未真正使用它**。本模块提供判据，但 `floating-agent-chat.tsx`
    还没接入 —— 组件切换（替换 `fetch`、接线回调、按开关分流）仍需完成，
    且需人工冒烟。
  - **`NEXT_PUBLIC_*` 是构建期替换**，因此**改这个变量需要重新构建/部署**，
    不是运行时可切的。若需要运行时切换，得走服务端配置 + 一个返回开关状态的
    接口 —— 那会增加一次请求，当前不值得。
  - **未做「灰度到部分用户」**。当前是全量开关，不是按用户百分比灰度。
    plan 没要求按用户灰度，但真要降低风险，下一步可以按 userId 哈希分流。
- **什么信号发生时该重访**：若切流后出现「请求 503」，
  先查部署顺序是否反了（客户端先于服务端）。`isSwitchCombinationSafe`
  就是为这种排查准备的。若需要按用户灰度，则要把它从环境变量改成
  服务端下发的配置。

# Agent Note: 工具执行层 —— 参数先校验、区块由工具名推导、只产出提案

Status: implemented

## Problem

`resume-tools.ts` 提供了 33 个**纯函数** builder：`(工作副本, 参数) → 提案`。
它们本身有测试覆盖，但从「模型发出一次工具调用」到「builder 产出提案」之间
还差三段接线，每段都对应一类真实缺陷：

1. **参数没校验就进 builder**。模型给的 JSON 不可信。旧实现把参数直接塞进去，
   于是超长文本、非法枚举、越权字段（`id`）会一路进到提交层才炸，报错也难定位。
2. **工具名与区块的关系没有约束**。五个排序工具（`reorderWorkExperiences` /
   `reorderProjects` / …）的工具名**已经**固定了区块，但原始 schema 还要求模型
   再填一次 `section`。这给了模型一次自相矛盾的机会：工具名叫 `reorderProjects`、
   `section` 填 `experience` —— 若调用方拿模型填的值去执行，就会静默重排错误的区块。
3. **没有「声明 / 参数 / 必需清单」一致性的检查**。声明的工具缺参数 schema、
   或写工具缺操作映射，都会表现为「模型调用了一个看起来存在但跑不起来的工具」，
   而模型通常会反复重试同一件事。

## Decision

新增 `lib/ai/tools/execute.ts` 作为执行层，集中三段接线：

### 1. 参数先校验再执行

按工具名取对应 zod schema（`ARG_SCHEMAS`），`safeParse` 失败即返回
`{ status: "failed", code: "invalid_args" }` 并**不执行工具**。只回传**第一条**
问题：列出全部会让模型难以选择要修哪一个。校验后使用**解析结果**而非原始
`args`（默认值与类型收敛都发生在解析里）。

### 2. 区块由工具名推导，不接受模型输入

`reorderItemsArgs` 去掉了 `section` 字段 —— 只有 `itemIds`。区块在执行层由
工具名通过 `matchArrayTool()` 推导。**工具名是服务端可验证的事实，模型填的
`section` 不是**；两者冲突时应当不存在「谁赢」的问题，因为根本不该有两个来源。

### 3. 加载期自检三者一致

`assertToolWiringComplete()` 在模块加载时跑一次，检查：

- 每条声明都有参数 schema（缺失 → 模型调用无法校验）；
- 每个 schema 都有对应声明（多余 → 死代码）；
- 每个写工具都有「工具名 → 操作种类」映射（缺失 → 提交层无法判断提案合法性）。

任何一条不满足直接抛错，**不让问题等到某个工具被调用时才暴露**。
运行期仍保留 `tool_not_implemented` 兜底：有人新增声明却忘了加分派时，
明确报错而不是返回空提案（后者会让模型以为操作成功了）。

### 4. 写工具只产出提案，绝不写库

执行层**不**调用 `commitResumeMutation`。提交由编排层在拿到提案后统一负责 ——
只有那里才有 run fence、幂等键与真实的 CAS 回执。把提交塞进工具内部会让
「同一轮两次写入」与「无回执却声称已保存」这两类问题重新出现（P03 已修过）。

只读工具（`readResume` / `suggestSkills` / `analyzeJobMatch`）返回 `read` 结果，
不产生任何提案。特别地，**`suggestSkills` 不再顺手写入 skills 区块**：
旧实现里一个名叫「建议」的工具会静默修改文档。

## Alternatives considered

- **让执行层直接调 `commitResumeMutation`，工具一步到位** — 调用方更省事，
  也少一层返回值。否决原因：提交需要 run fence、mutationId、CAS 基准，
  这些只有编排层持有；放进工具会让工具在测试里也必须接数据库，
  且会重新引入「同一轮两次写入」与「无回执声称已保存」。
  P03 的核心成果就是把这些收敛到唯一提交点，不能在 P04 拆开。
- **保留 `reorderItemsArgs.section`，但在执行层用工具名覆盖它** — 改动最小，
  且旧调用方仍能传 `section`。否决原因：「能传但会被忽略」的字段是最糟的形态：
  模型传错了不会有任何反馈，人读代码也看不出哪个来源是对的。
  直接删掉，让「区块只有一个来源」成为类型上的事实。
- **用 `switch (toolName)` 一条条穷举 33 个分支** — 最直白。否决原因：
  33 个分支里有 12 个是「区块 × 四个动作」的笛卡尔积，穷举会让改一个区块名
  要同时改四处。现在用 `matchArrayTool()` 从工具名反解，新增区块只加一行映射。
- **把参数解析失败当成「工具执行失败」事件发给用户看** — 否决原因：
  参数不合法是**模型的问题**，应作为工具结果回给模型让它自行修正，
  而不是弹给用户。返回 `failed` 会让编排层发 `tool.failed` 事件，
  这正确；但消息要写给模型看（说明哪个字段不合法），不是写给用户看的报错。
- **在加载期自检里 panic（直接崩溃进程）** — 更早暴露。否决原因：
  这是构建期/测试期的开发问题，抛异常已足够；让模块 import 就杀死进程
  会让「只想读一个常量」的调用方也受影响。

## Consequences

- **收益**：33 个工具从「有实现的纯函数」变成「可被模型调用且行为可预期」；
  越权字段与超长输入在进入 builder 前被拦；区块与工具名的错配在结构上不可能；
  接线缺口在模块加载时暴露而不是等到线上某次调用。
- **代价**：多一层 `execute.ts` 与一份 `ARG_SCHEMAS` 映射需要与新声明同步维护。
  自检把这件事变成机械约束（漏了就抛错），但仍是需要维护的重复信息。
- **已知上限**：执行层**不**校验提案里的操作是否属于该工具的 `produces` 声明。
  能力矩阵里有 `ToolDeclaration.produces`，`TOOL_OPERATION_MAP` 也有映射，
  但两者的一致性只在 `registry` 的测试里检查，执行层没有运行时交叉验证。
  若某个 builder 改了产出的操作种类而声明未更新，运行期不会报错。
- **什么信号发生时该重访**：若出现「工具提案里的操作种类与声明不符」的问题，
  就在执行层出口加一条交叉校验（拿 `TOOL_OPERATION_MAP[toolName]` 对比
  `proposal.operations.map(o => o.kind)`）。另外，若新增了工具却忘了加 schema，
  加载期自检会直接失败 —— 那时按报错提示补 `ARG_SCHEMAS` 即可。

## Verification

- 新增 `apps/web/tests/unit/ai-tools-execute.test.ts`（25 例）：
  - **一致性**：声明 33 条、声明/schema/必需清单三者对应、可用清单与声明一致；
  - **每个声明的工具都有执行入口**（穷举 33 个工具名，断言没有一个返回
    `tool_not_implemented`）；
  - **参数校验**：未知工具、缺必需参数、类型不符（`itemId` 给数字）、
    超长文本（20001 字符）全部 `invalid_args`；越权字段 `id` 被 schema 丢弃
    （断言实际 itemId 来自注入生成器而非模型输入）；
  - **写工具只出提案**：新增带顺序前置条件、更新按稳定 ID 定位、删除条件绑定
    整条内容、排序集合不一致时报 `order_set_mismatch`、单例写 `content` 字段、
    样式 `before` 是真实当前值（不是空对象）、隐藏模块的 before/after 正确、
    隐藏已隐藏模块报 `no_change` 而非假成功、自定义模块增改删排序均可用；
  - **只读工具不产生提案**（含 `suggestSkills` 不再静默写入）。

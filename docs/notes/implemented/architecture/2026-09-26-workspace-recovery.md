# Agent Note: 刷新恢复以服务端终态为准，四类错误各有可操作文案

Status: implemented

## Problem

P06 任务 6 要求两件事：

1. 「恢复后还原已完成工具、已应用/已拒绝建议及等待问题；
   **重放 event 不重复 toast/写入**」。
2. 「无终态 EOF、没有模型 key、未完成保存、找不到条目都有**可操作中文文案**」。

第一件事需要明确**谁负责去重**。`reducer.ts` 已有两层机制
（`seenEventIds` 精确去重 + `sequence` 单调性防乱序），并且有终态保护。
如果在恢复层再实现一遍去重，两处规则不一致时会得出互相矛盾的结论，
而排查时很难判断是哪一层放行了重复事件。

第二件事的关键在「可操作」三个字。只说「出错了」等于没说：
用户既不知道要不要重试，也不知道**自己的内容有没有丢**。

## Decision

新增 `lib/ai-client/workspace-recovery.ts`，纯函数：
`(事件数组, 服务端 RunStatus) → 工作区快照 + 错误类型`。

### 1. 去重完全交给 reducer，本模块只保证纯函数

`restoreWorkspace` 不自己判重，直接调 `reduceRunEvents`。它需要保证的是
**同输入同输出** —— 这样「刷新后重放同一批事件」不会让界面状态漂移。
测试断言的是「重放后数量不变」而非「本模块去重了」。

### 2. 服务端终态无条件优先于本地 interrupted

**这是我写错又改正的一处**。第一版写成
`completed && status !== "interrupted"`，方向反了。

事件流里的 `run.interrupted` 记录的是**某一次 attempt** 被中断（EOF / 超时），
而 Run 之后可能被别的 attempt 完成。服务端 `GET /runs/:id` 返回的是 Run 的
**最终状态**，比事件流里的一次 attempt 更权威。

若让本地 interrupted 覆盖服务端 completed，用户会看到「连接中断，未完成」——
但内容其实已经保存好了。那是**虚报失败**，会让用户白白重做一遍。

反之，服务端说 `running` 而本地已 EOF 时才保持 interrupted：
那是连接问题，不是 Run 结束。

### 3. 「未确认保存」需要三个条件同时成立

工具有成功、**有提案**、且**没有任何回执**。

第三条判据（要求有提案）是刻意的：诊断类任务只读、本来就不该有回执，
把它算成「未保存」会让用户以为出了问题。只有产生了修改意图却没有落盘回执，
才真正是「看起来做完了但没保存」。

这是整个任务里最需要诚实的一处 —— 它直接对应「模型完成 ≠ 已保存」。

### 4. 四类错误文案，每条都给出下一步

| 类型 | 文案要点 |
|---|---|
| 无终态 EOF | 说明是**连接中断**而非失败；已保存的修改不受影响；可重发 |
| 缺少模型 key | 给出具体入口（设置里连接模型服务） |
| 未完成保存 | 明确说「**还没有保存成功**、没有写入简历」；可重试或先复制 |
| 找不到条目 | 说明可能已被删除；给「刷新后重发」的步骤 |

文案里没有内部枚举名（测试断言 `message` 不含 kind 字面量）。

### 5. 错误推断的顺序是刻意的

先「找不到条目」→ 再「缺 key」→ 再「断线」→ 最后「未保存」。

理由：前三类会让用户的操作**根本无法完成**，而「未保存」是在操作已经发生
之后才需要提示的。先说前者能让用户少走弯路。

测试专门验证了这个顺序（即使同时缺 key，也应先说「找不到条目」）。

## Alternatives considered

- **在恢复层再做一次去重**（保险起见）— 看起来更安全。
  否决原因：两处去重规则不一致时会得出矛盾结论，且排查时难以定位。
  reducer 是权威，恢复层只做投影。若怀疑 reducer 去重有漏洞，
  应当在 reducer 里补测试，而不是在消费端加一层补丁掩盖它。
- **一律以本地事件流为准**（服务端状态只作参考）— 实现更简单，
  不需要处理两者不一致。否决原因：刷新后本地只重放**部分**事件，
  据此判断「还在运行中」是错的 —— 服务端早已结束，用户会一直等一个不会来的结果。
- **一律以服务端为准，忽略本地 interrupted** — 更简单。
  否决原因：服务端说 `running` 而本地 EOF 是真实场景（SSE 断了但 Run 还在跑），
  此时必须让用户知道可以重连。忽略本地信号会让界面一直显示「处理中」。
- **把「未确认保存」简化成「有工具成功但无回执」** — 少一个条件。
  否决原因：诊断类任务（只读）永远没有回执，会被误报成「未保存」。
  用户看到「内容没有写入简历」而实际什么都没打算写 —— 假警报会让真警报失效。
- **让错误文案只说「操作失败，请重试」** — 统一、简短。
  否决原因：plan 明确要求「可操作」。用户最需要知道的是自己的内容有没有丢，
  以及下一步该做什么。「请重试」对「未保存」这种场景远远不够。
- **在恢复层直接返回 `WorkspaceErrorKind`，不返回快照** — 职责更单一。
  否决原因：错误类型依赖快照内容（有无提案、有无回执、工具是否失败），
  分成两个函数会让调用方必须自己重算这些判据 —— 那正是把逻辑漏出去。
  因此合成一个 `restoreWorkspace`，并另给 `inferWorkspaceError` 供需要单独判断时用。

## Consequences

- **收益**：刷新后的界面状态有单一权威来源；「模型完成 ≠ 已保存」在 UI 层有
  明确的表达；四类错误都有可操作文案。
- **代价**：多一层恢复投影（reducer → 快照 + 任务卡）。
  `restoreWorkspace` 同时依赖两个模块（reducer、task-projection），
  改动任一个都可能影响它。
- **已知上限**：
  - **未接线到 UI**。`floating-agent-chat.tsx` 尚未调用 `restoreWorkspace`
    与 `describeWorkspaceError`。接线需要与该组件的刷新逻辑改造一起做。
  - **`unconfirmedWrites` 是个计数，不是清单**。UI 目前只能显示「有 N 处未确认」，
    不能列出具体是哪几处。要列出需要把工具与操作的对应关系也投影出来
    （`ToolCallProjection.changeSetId` 有部分信息，但不完整）。
  - **未处理「重连后补齐缺失事件」**。当前假设 `GET /runs/:id` 能返回
    服务端权威状态；若需要从某个 sequence 之后续读事件，那是另一个能力
    （`RunProjection.lastSequence` 已就绪，但没有消费它的续读逻辑）。
  - toast 去重未直接实现 —— 由「纯函数 + reducer 去重」间接保证。
    若 UI 层在每次事件到达时都弹一次 toast，仍会重复；那需要 UI 记录
    「已提示过的事件 id」。这一点留给接线时处理。
- **什么信号发生时该重访**：若用户反馈「刷新后看到连接中断但其实已完成」，
  检查服务端 `GET /runs/:id` 是否返回了终态（可能是本地覆盖了服务端）。
  若反馈「明明保存了却说没保存」，检查 `mutation.committed` 事件是否真的到达过客户端
  （可能是流式事件丢了回执，那属于 P04 的问题）。

## Verification

- `apps/web/tests/unit/ai-workspace-recovery.test.ts`（24 例）：
  - **恢复**：还原工具状态、还原等待问题、还原已应用/已拒绝决策；
  - **服务端优先**：本地不完整时以服务端为准、服务端 running + 本地 EOF
    不当作完成、failed/cancelled 如实反映；
  - **重放安全**：同输入同输出、**重放不产生重复工具/提案/提交**、不改动入参；
  - **未确认保存**：工具有成功+有提案+无回执 → 记为未确认；
    有回执 → 不算；**诊断类任务（只读、无提案）不报未确认**；
  - **四类文案**：每类都有可操作中文（匹配「可以/请/重试/不受影响/刷新」）、
    不含内部枚举名；四类各自的要点断言；
  - **推断顺序**：找不到条目优先于缺 key、缺 key 优先于断线、
    一切正常返回 null；
  - **interrupted 标记**：本地标记置位、**服务端 completed 时不置位**、
    idle 时不报断线。
- 红 → 绿：24 例中 2 例一开始失败，暴露了两处真实问题：
  ① 我把 `interrupted` 的优先逻辑写反了（本地覆盖服务端终态 → 会虚报失败）；
  ② 事件名与 payload 字段名写错（`decision.recorded` 的字段是
  `acceptedOperationIds` / `rejectedOperationIds`）。修正后 24/24 通过。

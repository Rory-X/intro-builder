# Agent Note: 浮窗消息 → 对话历史的映射规则与幂等键生成

Status: implemented

## Problem

`createFloatingRun`（协调层）接受 `history`，但**调用方必须自己从浮窗的
`messages` state 映射**。这条映射有几个**不显然的判断**，每一个都对应一类
真实的坏行为 —— 而它们都发生在「组件 2511 行 + 只在真实交互中才暴露」的位置：

| 判断 | 不做的后果 |
|---|---|
| 跳过流式生成中的消息 | 模型看到半句话，以为说过不完整的内容 |
| 跳过界面文案 | 模型看到一句自己从未说过的话 |
| 排除尾部当前消息 | 同一句话出现两次，模型以为用户重复说了 |
| 裁到服务端上限内 | 请求整体被拒（400），用户连当前这轮都发不出去 |
| 以用户消息开头 | 对部分模型是非法输入 |

另外 `requestId`（幂等键）的生成也有一个**双向陷阱**：服务端按它复用 Run，
而「复用」在两种场景下的正确答案**相反**。

## Decision

新增 `lib/ai-client/floating-history.ts`：纯函数，两道映射。

### 1. `buildHistoryFromMessages`：五条规则

**跳过 `streaming` 的消息。** 它的 `content` 是半句话 —— 送进历史会让模型
看到一句断掉的话。

**跳过界面文案**（`MODEL_MISSING_MESSAGE` 等）。那些是 UI 提示，
不是对话内容。把「尚未配置模型」送进历史会让模型看到一句自己从未说过的话。
文案集合**可覆盖**（不同组件有各自的占位文案，硬编码会让「跳过哪些」散在两处）。

**`excludeTail` 排除尾部当前消息。** 发起请求时当前这条用户消息会**单独**
作为 `message` 传给服务端（要单独校验长度、单独做意图判断）。
若它同时出现在 `history` 里，模型会看到同一句话两次。

**裁到 `AI_REQUEST_LIMITS.maxHistoryMessages`。** 复用 `trimHistory`
（它同时保证裁剪后以用户消息开头）。用**同一个常量**而不是写死 100 ——
服务端校验用的是它，两边写死会漂移。

**相邻同 role 同文本去重。** 流式追加可能让同一条消息被多次送入映射。
不相邻的重复**保留**（中间有别的对话，那是真实内容）。

### 2. `buildRequestId`：用序号而不是时间戳

幂等键的两种场景答案相反：

- **客户端重试**（网络抖动重发）→ **复用同一个键**，让服务端识别为重放
  而不是第二次修改；
- **用户再次提问** → **必须是新键**，否则命中上一轮的 Run 并返回
  「已复用既有任务」，用户看到的是「AI 没反应」。

因此键的构成是 `会话前缀 + 序号 + 消息哈希`：

- **不用随机 UUID** —— 那会让「重试复用同一键」不可能，而重试正是幂等键
  存在的主要理由；
- **不含时间戳** —— 时间戳看似唯一，但快速连点时同一毫秒内两次调用的
  前缀相同、哈希输入相同，必然撞键。序号是可靠区分器；
- 消息 `trim` 后参与哈希（避免同一句话因空格差异产生多个键）。

## Alternatives considered

- **在组件里内联这段映射** — 少一个模块。否决原因：那是 2511 行组件里
  最难测到的一处（要 mock 整个组件环境），而这五条规则每条都有具体的坏行为。
  抽成纯函数后 29 例可以直接穷举。
- **历史里包含工具调用** — 上下文更完整。否决原因：历史是**文本**，
  无法表达「那次提交是否成功」。把工具调用放进去会让模型以为
  「这些操作已经做过了」—— 在某些情况下确实如此（有回执），
  但历史文本无法区分。模型的下一步决策应基于**当前文档状态**
  （在系统提示里），而不是对历史操作的记忆。
- **`requestId` 用 `crypto.randomUUID()`** — 最省事，且天然不撞键。
  否决原因：**它让重试无法复用键**。用户在弱网下重发会触发第二次模型执行 ——
  既烧额度，又可能产生两次内容修改。序号方案同时满足两个相反需求。
- **`requestId` 含时间戳** — 看起来唯一。否决原因：同毫秒连点会撞键。
  而「连点两次发送」正是最常见的用户行为之一。
- **不跳过界面文案，靠服务端过滤** — 客户端更简单。
  否决原因：服务端不认识这些文案（它们是界面层的字符串常量）。
  放在映射处过滤是唯一能做对的地方。
- **不裁剪，超限时让服务端拒绝** — 语义直接。否决原因：用户看到
  「请求失败」而真实原因是「对话太长」，他既不知道要删什么也不知道怎么继续。
  客户端裁到上限内至少让对话能走下去。
- **映射时不校验 `maxMessages`，只用默认值** — 少一个参数。
  否决原因：测试需要能构造「小上限」来验证裁剪与「以用户消息开头」。
  且将来若上限策略变化（例如按模型调整），有参数才好扩展。

## Consequences

- **收益**：切流仍缺的最后一处纯逻辑就位；五条映射规则各有测试；
  幂等键的两种相反场景都有明确答案。
- **代价**：多一个模块（约 150 行 + 29 例测试）。
- **已知上限**：
  - **仍未被真实调用**。`createFloatingRun` 与这两个函数都还没接到
    `floating-agent-chat.tsx` —— 组件切换（替换 `fetch`、接线回调、
    翻转默认 surface）仍需人工冒烟。
  - **`sequence` 由调用方维护**。本模块不持有状态（纯函数），
    因此「序号递增」需要组件自己保证。若组件漏了递增，同一消息的两次发送
    会撞键 —— 而症状是「AI 没反应」（命中复用），不易定位。
  - **界面文案集合与组件实际文案可能不同步**。默认值里列了三条常见文案，
    但组件里的常量若调整，这里不会自动跟随。可考虑的改进是让组件把
    自己的文案常量传进来（`uiOnlyMessages` 已支持）。
  - **不合适做「按 token 裁剪」**。当前只按条数；长消息（每条接近
    20000 字符上限）时 100 条体积仍可能很大。
- **什么信号发生时该重访**：切流后若用户反馈「发第二次没反应」，
  先查 `sequence` 是否真的递增（症状正是命中复用）。
  若反馈「AI 忘了我前面说的」，检查是否误跳过了某些应保留的消息
  （例如 `streaming` 判断把已完成的也跳过了）。

## Verification

- `apps/web/tests/unit/ai-floating-history.test.ts`（29 例）：
  - **基础映射**：顺序、trim 空白；
  - **跳过流式消息**：streaming 不进历史、已完成的照常进入；
  - **跳过界面文案**：模型未配置提示不进入、**可自定义集合**、
    空内容不产生条目；
  - **排除尾部**：`excludeTail=1` 时当前轮不进历史且不出现在结果里、
    超长时返回空、负数按 0 处理；
  - **去重**：相邻同 role 同文本跳过、**不同 role 同文本不去重**、
    不相邻的重复保留；
  - **裁剪**：超限保留最近且不超上限、**裁剪后以用户消息开头**、
    可自定义上限、上限为 0 返回空；
  - **边界**：空列表、全是界面文案时返回空、纯函数、不改动入参；
  - **幂等键**：**同输入同键**（重试复用的前提）、
    **序号不同则键不同**（再次提问必须新建）、消息不同则键不同、
    会话不同则键不同、无会话用 anon 前缀、
    **不依赖时间戳**（同毫秒连点 5 次得到 5 个不同键）、
    带可读会话前缀、消息首尾空白不影响键。
- 全量：`pnpm test` 1721 例通过、`typecheck` 四包全绿、
  `lint` 0 error（12 warning = 基线）。

# Agent Note: 提案卡组件 —— 本地勾选与投影决策是两回事

Status: implemented

## Problem

P06 任务 3/7 要求把提案卡投影接到 UI，plan 文件范围点名列了
`components/agent/resume-change-set-card.tsx`。

接线时踩到一个**真实的坑**：我第一版用投影的 `card.canApply` 控制「应用」
按钮的可用性，结果**用户勾选后按钮仍然禁用** —— 界面看起来坏掉了。

根因是两个不同的东西被我混成了一个：

- `card.canApply` 基于**投影里已接受的操作**（`card.accepted`，来自持久化的
  决策状态）；
- 用户此刻是在**本地勾选**（组件的 `selected` state）。

`canApply` 为 false 时（用户还没做任何持久化决策），本地勾选再多也不生效。

## Decision

### 1. 按钮可用性看本地选中 + 提案是否终态

```ts
const isTerminal = card.status === "committed" || card.status === "rejected";
const canSubmit = !isTerminal && applicable.length > 0;
```

`applicable` 是「本地选中且不在冲突集里」的操作。冲突必须先处理 ——
让用户点出一个必然被服务端拒绝的组合是更差的体验。

**这不涉及「是否已保存」的判断**：落盘只看提交回执。组件的按钮文案是
「应用」而不是「保存」，且测试断言卡片上**不出现「已保存」**。

### 2. 折叠用投影给的 `visibleGroups`

组件**不自己写**「折叠时保留冲突组」的过滤逻辑，而是调
`visibleGroups(card, { collapsed })`。

必要性：两处各写一份会漂移，而漂移的后果是**冲突被折叠掉** ——
用户看不到就无法处理。这条是 plan 明确要求的（「冲突组保持可见」）。

折叠时如实显示「已收起 N 组修改」，而不是让用户以为没有别的内容。

### 3. 有依赖的项禁用勾选，并说明原因

`canAcceptIndividually` 为 false 时禁用 checkbox，并显示
「这一项依赖上面新增的内容，需要一起接受」。

只禁用不说明会让用户困惑（「为什么点不动」）。

### 4. 点击定位传投影给的 target

`onLocate(item.target)` —— `{ section, itemId, field }`，**不是下标**。
测试断言回调参数不含 `index`。

## 实测修正的两个问题（红 → 绿）

21 例中 2 例一开始失败：

**一、勾选后按钮仍禁用**（上面第 1 点）。这是**组件的真实缺陷**，
由测试「勾选后已选计数增加，应用按钮生效」抓出。

**二、测试自身的选择器不唯一**：两个组的操作都是「改 company」，
标签都是「修改公司」，`getByText` 找到多个元素。
这不是组件问题，而是我的测试构造不当。改用不同字段
（`company` / `title`）让断言唯一 —— 顺带让「折叠保留冲突组」这条
断言更强（能验证非冲突组确实被收起）。

## Alternatives considered

- **用 `card.canApply` 控制按钮**（我第一版的做法）— 少一个判断。
  否决原因：它把「持久化的决策状态」与「本地勾选」混为一谈，
  结果是用户勾选后按钮不动。这种 bug 很容易漏掉，
  因为在不勾选任何东西的默认状态下按钮本来就是禁用的，看起来「正常」。
- **勾选后立刻发写请求**（自动应用）— 少一次点击。
  否决原因：plan 要求「生成中不偷改正文」，且批准与落盘是两件事。
  自动写会让用户无法反悔，也绕开了统一提交路径的 revision 校验。
- **组件自己实现折叠过滤**（`groups.filter(g => g.hasConflict)`）—
  不依赖投影函数。否决原因：那正是两处规则漂移的开始。
  投影层的 `visibleGroups` 有专门的测试（32 例里的断言），
  组件再实现一遍等于把那条测试覆盖的逻辑复制到没有测试的地方。
- **折叠时把冲突组也收起，用顶部提示代替** — 界面更干净。
  否决原因：plan 明确要求冲突组保持可见。冲突需要**逐项**处理
  （哪一条冲突、当前内容是什么），一条汇总提示承载不了这个信息。
- **「应用」按钮文案改成「保存」** — 用户更熟悉。
  否决原因：那个词暗示「已经写进去了」，而点击后还需要走提交并等待回执。
  「应用」表达的是「把这些改动提交上去」，更接近实际语义。
- **卡片上显示一个「已保存」徽章**（当 `status === "committed"`）—
  否决原因：`status === "committed"` 表示**提案**被标记为已提交，
  不等于文档内容落盘（冲突场景下两者可能不一致）。
  这类判断只能由提交回执驱动，与任务卡的处理一致。

## Consequences

- **收益**：提案卡可用（本地勾选能正确驱动按钮）；冲突在折叠时仍可见；
  依赖项不能造出必然失败的组合；「批准 ≠ 已保存」在组件层仍然成立。
- **代价**：多一个组件与一份 RTL 测试；调用方需要负责投影（调
  `buildChangeCard`）与真正的提交。
- **已知上限**：
  - **尚未接入 `floating-agent-chat.tsx`**。组件可用但**没有真实调用方**，
    因此「在实际会话中显示提案卡」尚未完成。接线需要改那个大组件。
  - **`onLocate` 的实际定位行为未实现**。组件会回调 target，
    但调用方如何滚动/高亮到正文对应位置还没有代码 ——
    那需要编辑器侧提供「按 section+itemId+field 聚焦」的能力。
  - **分组接受未限制整体性**：有依赖的项禁用勾选，但用户可以取消勾选
    组内第一条而保留第二条（第二条此时已禁用，因此实际做不到）——
    这个组合恰好被禁用规则挡住了，但规则本身是「单项禁用」而非「组级约束」。
    若将来支持组级勾选，需要显式处理。
  - 未做键盘导航的完整验证。
- **什么信号发生时该重访**：若用户反馈「勾选了但应用按钮还是灰的」，
  检查是否有人把 `canSubmit` 改回了基于 `card.canApply`。
  若要实现点击定位，需要在编辑器侧提供按 `itemId` 聚焦的能力
  （`locateOperation` 已给出所需标识）。

# Agent Note: 提案卡按依赖分组，冲突组在折叠时仍可见

Status: implemented

## Problem

P06 任务 3 要求「一组任务对应一张 changeSet 卡；显示**具体位置、前后差异、理由、
事实来源、批准/拒绝状态**。点击定位稳定 itemId；生成中不偷改正文。
**允许依赖无关组部分接受，冲突组保持可见**」。

把操作列表平铺渲染是最省事的做法，但它有三处会真实伤到用户：

1. **平铺会造出必然失败的组合**。一组操作里常有依赖：
   「新增一条经历」+「往这条经历里写内容」。平铺后用户可以只接受后者 ——
   而那是一条指向不存在目标的命令。服务端会拒绝（P04 的 `validateDecision`
   有依赖检查），但让用户点出一个必然失败的组合是更差的体验。
2. **按下标定位会跳错地方**。UI 点击卡片项要跳到对应内容；下标在内容变化后
   指向别的条目，用户点「第三条经历」会跳到别处。
3. **把「已批准」显示成「已应用」**。批准与落盘是两件事
   （P04 的决策路由已用 `awaiting_commit` 表达这一点），卡片必须沿用同一区分。

## Decision

新增 `lib/ai-client/change-set-card.ts`，纯函数：`提案 + 决策 → 卡片`。

### 1. 按 itemId 分组，而不是按语义猜

分组规则只看一件事：**哪些操作引用了同一个 `itemId`**。
`insert_item` 与指向该新 itemId 的 `set_field` 因此自然同组。

不按「操作种类」或「字段相关性」猜 —— 那些判据都需要额外规则，
而「引用同一个目标」是机械且无歧义的。组内后续项声明 `dependsOn: [第一条]`，
`canAcceptIndividually` 据此返回 false，UI 可以禁用单项接受按钮。

### 2. 冲突组在折叠时保留

`visibleGroups(card, { collapsed })` 在折叠时**只返回有冲突的组**，
而不是返回空数组。plan 明确要求「冲突组保持可见」——
把它单独做成函数，是因为放在渲染逻辑里容易被「折叠就全折叠」的直觉覆盖。

### 3. `canApply` 表达「可以提交」，不表达「已保存」

三个条件：有接受的操作、该操作不在冲突集里、提案未终态。

刻意**没有** `saved` 字段：那只能来自提交回执。测试专门断言
`card` 不含 `saved` / `committed` 属性 —— 防止有人图省事加一个，
让卡片自己声明「已保存」。

### 4. 定位返回 itemId，不返回下标

`locateOperation` 返回 `{ section, itemId, field }`。测试断言
序列化结果里不含 `index` —— 下标一旦进入这个结构，就会有人拿它跳转。

## 实测发现并修复的两个缺陷（红 → 绿）

### 缺陷一：`set_field` 的 `before` 是两个分支都返回 null 的笔误

第一版写成 `before: readableValue(operation.value) === null ? null : null`。
结果恰好正确（`set_field` 操作本身确实不带 before 值），但语义混乱。
更根本的是：**条件哈希不是原文**，卡片拿不到「改前」值。因此显式写
`before: null` 并注明「展示层需要改前值时应当从当前文档读取（定位由
`locateOperation` 给出），而不是从操作里编一个」。

### 缺陷二：`insert_item` 的 `after` 是空的

`readableValue` 对普通对象直接 `return null`，于是「新增一条工作经历」卡片上
`after` 为空 —— 用户只看到「新增」两个字，看不到新增了什么。

测试抓到这一点（`expected null to be '甲公司'`）。改为挑出可读字段值拼成短摘要
（跳过 `id` 与富文本结构，最多 4 个字段）。

顺带加了**深度保护**：`insert_item.value` 在契约里是 `z.record(z.unknown())`（无界），
深层嵌套会让递归爆栈 —— 而这是用户可见的渲染路径，崩在这里比显示得简略更糟。

## Alternatives considered

- **平铺操作列表，把依赖检查留给服务端** — 实现最简单，且服务端确实会拒绝
  非法组合。否决原因：让用户点出一个必然失败的组合，失败后还得读错误信息
  才知道「这两条要一起接受」。分组让这件事在点击前就成立。
- **按「操作种类」分组**（所有 set_field 一组、所有 insert_item 一组）—
  分组规则更直白。否决原因：同种类的操作常常作用在不同条目上，
  按种类分组会让「改 A 公司名」与「改 B 公司名」落在同一组，于是必须整体接受 ——
  这与 plan 要求的「依赖无关组部分接受」正好相反。
- **`canApply` 加上「是否已保存」** — UI 少读一个字段。否决原因：
  卡片拿不到回执，它只能知道自己被标成了什么状态。加一个 `saved` 字段的结果是
  有人会把它写成 `status === "committed"` —— 而「提案被标为已提交」与
  「文档真的落盘了」在冲突场景下并不等价。
- **`readableValue` 对普通对象返回 `JSON.stringify`** — 一行搞定。
  否决原因：用户会看到 `{"company":"甲公司","title":"工程师",...}`。
  这个字段的用途是「让用户一眼看出改了什么」，塞 JSON 等于没做。
- **冲突组折叠时也隐藏，用顶部一条提示代替** — 界面更干净。
  否决原因：plan 明确要求冲突组保持可见。冲突需要用户**逐项**处理
  （哪一条冲突、当前内容是什么），一条汇总提示无法承载这个信息。

## Consequences

- **收益**：卡片不会造出必然失败的组合；冲突项在折叠时仍可见；
  定位用稳定 ID；「已保存」这件事无法从卡片上被误读。
- **代价**：多一层分组逻辑与一份区块/字段的中文映射表。
  新增区块或字段时必须同步加标签，否则用户看到英文标识符。
- **已知上限**：
  - **未接线到 UI**。本模块只提供计算，`floating-agent-chat.tsx` 尚未使用它。
    与任务 2 的任务卡一样，接线需要与浮窗改造一起做。
  - **`before` 值缺失**。`set_field` 操作不带原文（只带条件哈希），
    因此卡片无法显示「改前是什么」。要显示需要调用方额外传入当前文档，
    由 UI 按 `locateOperation` 的结果去读 —— 本模块没有做这件事。
  - **「事实来源」（evidenceRefs）未实现**。plan 要求卡片显示事实来源，
    而当前操作契约里没有 evidenceRefs 字段（spec §6 的 `Advice` 类型有，
    但那是评测侧的 artifact，尚未进入提交契约）。这是**真实缺口**，
    需要先在契约里加字段，不能靠投影层编造。
  - 分组只看 itemId：若将来出现「跨条目的依赖」（例如「删除 A 之前先改 B」），
    当前规则不会把它们分到一组。
- **什么信号发生时该重访**：若要在卡片上显示「改前/改后」对比，
  需要扩展 `BuildChangeCardInput` 接收当前文档快照。
  若要实现事实来源，先在 `SemanticOperation` 或提案记录里加 evidenceRefs 字段
  （属于契约变更，需要 spec 支持）。

## Verification

- `apps/web/tests/unit/ai-change-set-card.test.ts`（32 例）：
  - **基础投影**：稳定 itemId 与位置描述、标签是业务语言（不含字段名/JSON path）、
    summary 作为理由兜底、totalCount；
  - **依赖分组**：**insert + 指向新条目的 set_field 同组**、组内后续项声明依赖、
    不同条目分到不同组、**有依赖的操作不能单独接受**、无依赖可单独接受；
  - **冲突组可见**：冲突标记落到组、**折叠时冲突组仍可见**、不折叠时全部可见、
    冲突使 canApply 为 false、无冲突接受时可应用；
  - **canApply 三条件**：无接受 → false、已 committed/rejected → false、
    partially_committed 仍可应用；**卡片上不含 saved/committed 字段**；
  - **定位**：返回 section/itemId/field、找不到返回 null、
    **序列化结果不含 index**；
  - **各操作展示**：新增（带内容摘要）、删除（醒目）、重排（前后顺序）、
    模块顺序、样式（只展示改变的键）、标题与模板、
    **富文本渲染成纯文本**（不含 `doc`/`paragraph`）、数组渲染成顿号分隔；
  - **决策状态**：accepted/rejected 原样保留、proposalVersion 带出。
- 红 → 绿：32 例中 1 例一开始失败（`insert_item` 的 `after` 为空），
  暴露了 `readableValue` 对普通对象直接返回 null 的缺陷。修正后 32/32 通过。
- 全量：`pnpm test` 1408 例通过、`typecheck` 四包全绿、`lint` 0 error。

# Agent Note: 条件撤销接通 —— 用 inverse 还原字段，而非回退整版

Status: implemented

## Problem

`prepare.ts` 为每个应用的操作生成 `inverse`，注释明确写着「是条件撤销的依据」。
但**全仓库没有消费者** —— 撤销链路完全未接线。

具体缺两段：

1. `commitResumeMutation` 把 `prepared.inverse` 算出来了却没放进返回值，
   调用方拿不到它；
2. 没有「由 inverse 构造一份撤销命令」的入口，
   因此 `CommitPrincipal.undoOf` 与 `source: "undo"` 这两个早就存在的字段
   从未被任何调用方填入。

## 撤销的正确语义（plan 验收把它钉死了）

plan 的用户可见验收写着：「**修改 A 后用户补技能，再撤销 A，技能仍保留**」。

这一句把两种做法分开了：

- **错的**：把内容整体回退到 A **之前**的状态。那会把用户随后补的技能一起抹掉 ——
  而用户只想撤掉 A。这也是「恢复整版」（`commitResumeRestore`）的语义，
  plan 要求它「明确提示并走 commit」，与撤销是两回事。
- **对的**：用 `inverse` 把 **A 改过的那些字段**还原，其它字段不动。

因此本模块的核心是「用 inverse 构造一份新的条件命令」，而不是「找到旧快照并恢复」。

## Decision

### 1. `CommitOutcome` 加可选 `inverse` 字段

只在**首次提交**路径返回。幂等重放走 `existing` 分支，而回执表里没有存 inverse ——
这是如实的：重放不产生新的反操作，撤销应当针对**原来那次**提交的 inverse。

刻意**不**放进 `CommitResult` 契约类型：那是面向客户端的 API 响应形状，
而反向操作是内部能力，不该出现在契约里。

### 2. 三条必须守住的事

**操作 id 重新生成**（加 `:undo` 后缀）。直接复用 `:inverse` 的 id 会让撤销与
原提交共享 operation id，提交层的 `operationIds` 记录就无法区分两者。

**幂等键是新的提交**，且**必须与被撤销命令不同**。这条有专门拦截：
若相同，服务端会把它识别为幂等重放而返回原回执（即「什么都没发生」），
用户看到撤销「成功」但内容没变 —— 一个静默失败。

**空 inverse 一律拒绝**。没有反操作意味着「无可撤销」，
静默返回成功会让用户以为撤掉了什么。

### 3. 条件哈希由当前文档重算

`inverse.condition.expectedValueHash` 是 A 提交**当时**算出的「A 之后的值」。
撤销发生在之后，期间目标可能已被改过。

直接拿旧哈希去提交会有两种后果，都不可接受：服务端接受 → 用过期条件做了写入，
等于无条件覆盖（丢失期间改动）；服务端拒绝 → 用户看到「撤销失败」但不知道原因。

因此正确做法是**用当前文档重算条件**：目标仍等于 A 之后的值时才允许撤销，
若已被改过则返回可操作的冲突说明。测试专门覆盖了这条
（撤销前有人把值改成「丙公司」→ `condition_mismatch`）。

### 4. 破坏性撤销要能被识别

撤销一次「新增」的反操作是「删除」——这是破坏性的，UI 应二次确认。
`undoIsDestructive` 供 UI 判断。撤销一次「删除」的反操作是「新增」，
不是破坏性的（它只是在恢复内容）。

## Alternatives considered

- **把 inverse 放进 `CommitResult` 契约** — 调用方从返回的 `result` 里直接读，
  少一个字段。否决原因：`CommitResult` 是客户端可见的 API 响应形状。
  把内部的反向操作塞进去会让它成为契约的一部分 —— 将来想调整 inverse 的
  表示方式就成了破坏性变更。放在 `CommitOutcome`（内部类型）里没有这个问题。
- **撤销时让服务端自己从版本记录里算 inverse** — 客户端不用传操作，
  只需说「撤销这个版本」。否决原因：那需要服务端重新执行一遍 `prepare` 才能
  得到 inverse，而 `prepare` 需要**当时的**内容与 `newItemId` 生成器 ——
  版本记录里存的是结果快照，不是生成 inverse 所需的全部输入。
  把 inverse 在提交时算好并交给调用方，是成本更低且更可靠的路径。
- **撤销实现成「恢复整版快照」**（拿 A 之前的版本内容整体写入）—
  实现最简单，一次提交搞定。否决原因：这正是 plan 验收要防的
  「撤销 A 会抹掉用户随后补的技能」。整个功能的价值就在「只撤 A 改过的部分」。
- **允许 `mutationId` 与被撤销命令相同** — 代码更少。否决原因：
  服务端会把相同 mutationId + 相同 payload 识别为幂等重放，返回原回执。
  于是「撤销」的响应是「已提交」，但内容没有任何变化 ——
  用户会以为撤销成功了。这类静默失败必须显式拦住。
- **空 inverse 时静默返回成功** — 用户点了撤销能看到「成功」提示。
  否决原因：那是谎报。没有反操作就是没撤任何东西，
  必须告诉用户「这次修改没有可撤销的内容」。
- **让 UI 自己计算 inverse** — 投影层已经有完整操作列表。否决原因：
  inverse 的生成依赖当前内容（条件哈希）与操作语义（插入的反操作要知道前一条 id），
  在 UI 重算会重复实现 `prepare` 的逻辑，且极易算错 ——
  而算错的后果是写入错误内容。

## Consequences

- **收益**：撤销链路接通；语义是 plan 验收要求的那一种（只还原 A 改过的字段）；
  三种静默失败（幂等键复用、空 inverse、条件过期）都被拦住或如实报告。
- **代价**：`CommitOutcome` 多一个可选字段；调用方需要自己保存首次提交的
  `inverse` 才能在之后撤销（服务端不提供「查历史 inverse」的能力）。
- **已知上限**：
  - **仍缺读取层与 UI 接线**。本提交只打通了「提交层产出 inverse → 构造撤销命令」
    这一段。要让用户真的能点撤销，还需要：
    ① 读取层取出 `mutationId`/`undoOf`（`version-history` 的 `VersionRecord` 已定义
    所需字段，但查询尚未取出）；
    ② 一个把「版本记录 → 撤销提交」串起来的路由或 action；
    ③ UI 的撤销入口与二次确认（破坏性撤销时）。
  - **inverse 不持久化**。它只在首次提交的返回值里出现。
    若调用方没保存，之后无法撤销 —— 因为回执表没存它。
    持久化 inverse 是可行的改进（加一列 jsonb），但会让回执体积变大，
    当前没有做。
  - 未支持「撤销的撤销」（重做）。`undoIsDestructive` 与
    `version-history.canUndo` 都排除了撤销记录本身。
- **什么信号发生时该重访**：若用户反馈「撤销后别的改动也没了」，
  说明撤销被实现成了整体回退（本笔记第「正确语义」节要防的错误）。
  若反馈「点撤销没反应」，先查调用方是否保存了首次提交的 inverse。

## Verification

- `apps/web/tests/unit/undo-command.test.ts`（15 例）：
  - **构造**：由 inverse 构造命令并带 `undoOf`、**操作 id 重新生成**、
    **幂等键相同被拒**（否则静默失效）、**空 inverse 被拒**、缺目标被拒；
  - **plan 验收**：**撤销 A 只还原 A 改过的字段，用户随后补的技能被保留**
    （用真实 `prepareMutation` 生成 inverse 并在含后续改动的文档上应用）、
    **条件不成立时撤销被拒**（`condition_mismatch`，避免用旧建议覆盖新输入）；
  - **破坏性识别**：撤销「新增」是破坏性的、撤销字段修改不是、
    撤销「删除」是「新增」且不是破坏性的；
  - **失败说明**：条件不成立时明确「未覆盖你的改动」、每种情况有专门说明
    且不含原始码、未知码有兜底；
  - **接线**：`prepare` 返回非空 inverse、无变化时 inverse 为空。
- 全量：`pnpm test` 1448 例通过、`typecheck` 四包全绿、`lint` 0 error。

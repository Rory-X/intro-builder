# Agent Note: 提示词模块化、版本可归因与意图识别由程序决定

Status: implemented

## Problem

提示词长期是一个每轮现拼的长字符串（旧浮窗 6 行 + 动态分支 + 2000 行路由里的
工具描述），带来三个具体问题：

1. **泛化建议**。旧稿的失败模式是模型回「建议突出亮点、加强量化、采用 STAR」——
   用户拿不到可用内容。这不是模型能力问题，而是提示词只说了「要具体」，
   没说清什么算具体、以及明确不要做什么。
2. **评测结论无法归因**。契约要求「promptVersion 独立配置，保留上一版，
   指标退化可只回滚提示词」。但只要版本号与正文没有绑定，「v1 得分 8.4」
   这句话就没有确定含义 —— 文本被人改过之后，分数仍然挂着 v1 的名字。
3. **意图边界靠模型自选**。模型若能自己决定「本轮是诊断还是改写」，
   等于能自己放宽约束。

## Decision

新增 `lib/ai/prompts/`，按 spec §2 的装配次序拆成五块：
`core.ts`（候选稿正文）、`intent.ts`（六种意图的补充约束 + 程序侧识别）、
`examples.ts`（最多两条演示示例）、`assemble.ts`（装配与分段）、
`version.ts` + `registry.ts`（版本与哈希）。

### 1. 版本 = 正文 + 内容哈希，加载期自检

`registry.ts` 登记每一版的 `contentHash`，模块加载时重新哈希正文比对。
不一致就抛错。

这让「回滚提示词」成为可验证的动作：回滚到的确实是当初评测过的那一份文本。
只改文本不改哈希（或反过来）会在启动时立即失败，而不是让旧结论悄悄挂到新文本上。

`legacy` 的哈希由**真实快照文本算出**而不是硬编码，理由相同：
硬编码会让「文本改了但哈希忘了改」变成需要人工发现的错误。

### 2. 旧稿逐字节冻结

`legacy.ts` 保存合并前 `buildFloatingSystemPrompt` 与润色 prompt 的正文，
供对照评测作固定基线。已用脚本逐字节比对确认与实现一致
（两者 SHA-256 相同：`929d5f7e…`）。

必要性：旧实现位于待退役的微服务里，迁移过程中随时可能被删改。
冻结在这里，评测基线就不会随迁移进度漂移。

### 3. 示例必须标注「演示」，且每轮最多两条

示例里的技术名被写进用户简历是真实发生过的失败（评测集 Q03 类硬失败）。
因此：

- `assertExamplesAreSafe` 在加载期检查每条示例的 `scenario` 含「演示」，
  缺标注直接抛错；
- `selectExamples` 的条数上限是机械的（`Math.min(limit, 2)`），
  不靠调用方自觉 —— spec 要求「只注入相关的 1–2 个」，而「相关」的判定容易越放越宽；
- 渲染时显式声明「其中的姓名、公司和技术均为演示，不得作为用户事实写入简历」。

### 4. 意图识别由程序决定，且**先识别用户要求的动作**

`resolveIntent` 的判据是显式 UI 上下文 + 确定性关键词。无法判定返回 `null`，
由装配层走保守路径，不猜。

顺序上有一条关键修正：**先识别用户明确要求的动作，再判断「是否只是一个回答」**。

## Alternatives considered

- **把提示词全部内联在路由里，靠 git 管版本** — 最简单，少两个模块。
  否决原因：git 能做到「看到历史」，做不到「证明某个分数属于某份文本」。
  契约明确要求回滚提示词不影响代码，而 revert 一次提交会把代码一起退回去。
- **版本号写在文件名里**（`core-v1.ts`）而不做哈希校验 — 更直观，
  不需要登记表。否决原因：文件名不阻止有人在原地改正文。
  哈希校验的价值恰好在于「改了就会立刻被拦住」。
- **让模型自己判断本轮意图**（把六种约束全给它，让它选） — 少一层程序逻辑。
  否决原因：那等于把约束的选择权交给被约束者。用户说「只诊断」时，
  模型可以自选 rewrite 并直接改文档 —— 这正是评测集 Q05 的硬失败项。
- **意图识别用语义相似度 / 小模型分类** — 判定更准，能覆盖更多说法。
  否决原因：误判的代价不对称。判错的后果是模型做了用户没要求的事
  （例如只诊断变成重写），而用户无法解释为什么。确定性关键词的误判是
  「判不出来就返回 null」，这个失败模式安全得多。
- **回答类判定用前缀匹配**（`/^(是|嗯|对)/`）— 我第一版就是这么写的。
  否决原因：实测发现它会把「**是的，帮我改一下**」判成 `fact_intake`，
  于是用户明确的改写请求被套上「只追问、不改正文」的约束，
  表现得像模型没听见。同时「是否…」「有没有…」这类**疑问句**也被误判。
  改为整句匹配 + 排除省略号（`是……` 是犹豫不是确认）。
- **保留旧稿的强制 STAR 四段结构** — 输出结构稳定，便于解析。
  否决原因：spec §5 明确把「套四段 STAR」列为无效做法（示例 D、Q04）。
  候选稿改为「STAR 用于检查信息是否清楚，不要求输出四个英文标题」。
- **不冻结旧稿，评测时从 git 历史取** — 不占仓库空间。否决原因：
  旧实现在待退役的微服务里，从 git 取意味着评测依赖「那个文件还在」，
  而它的删除正是本切片的目标之一。

## Consequences

- **收益**：提示词可独立版本化与回滚，且回滚可验证；泛化建议有了明确的
  禁止清单与正例；JD 与用户事实在结构上分开（Q03 防线）；
  示例污染事实被机械拦住；意图边界由程序守，模型无法自行放宽。
- **代价**：提示词从「一个字符串」变成 6 个文件 + 登记表，改动需要同步更新
  哈希（有意的摩擦力）；装配多一层间接。
- **已知上限**：
  - 候选稿的**效果尚未评测**。本次只落地了模块化、版本机制与契约测试；
    spec §8 要求的 16×2×3=96 次真实对照评测**未运行**（`not_run`），
    因此不能声称候选稿优于旧稿。这属于 plan 写明的停止条件
    （「没有显式可用评测配置不能假造分数」）。
  - `resolveIntent` 的关键词表是第一版，覆盖有限。它会漏判（返回 `null`），
    这在当前设计下是安全失败，但意味着部分轮次拿不到意图约束。
  - `assemble.ts` 的分段标记是「软边界」——它降低而非消除注入风险。
    Q11（材料含「忽略指令」）需要在真实模型上验证，属未跑的评测范围。
  - 工具能力清单（`toolCapabilities`）的文本生成尚未接线到真实注册表。
- **什么信号发生时该重访**：跑完真实对照评测后，若候选稿在某些案例上不如旧稿，
  按 spec §8 记录例外证据并重新评审阈值（**不篡改结果凑过线**）。
  若出现「模型做了用户没要求的事」，先看 `resolveIntent` 是否误判
  （关键词过宽），而不是先去改 core。

## Verification

- `apps/web/tests/unit/ai-prompt-contract.test.ts`（47 例）：
  - **版本**：登记哈希与正文一致、legacy 哈希来自快照、篡改文本被检出、
    CRLF/LF 规范化、中间空白**不**折叠（否则不同文本撞哈希）、
    未知版本抛错、两版正文不同；
  - **旧稿快照**：保留 direct 分支且不含 approval 分支、润色 6 条规则齐全；
  - **core 候选稿**：明确禁止泛化建议、禁止编造事实、区分三种证据状态、
    JD 定义为材料、三种保存状态齐全、不要求 STAR 四段、长度 < 1200 字符；
  - **意图**：六种意图齐全且都有禁止行为（逐条与 plan 表格比对）、
    渲染区分「要求/有效输出/禁止」；
  - **意图识别**：UI 上下文优先、四类关键词识别、**回归防线**
    （「是的，帮我改一下」判为 rewrite、疑问句判 null、省略号判 null）；
  - **示例**：加载期自检、缺标注被拒、上限两条、只选相关意图、
    无意图不注入、顺序稳定、渲染含「不得作为用户事实」、覆盖 plan §5 五个场景；
  - **装配**：次序正确、core 最前、分段带 sourceId 与边界声明、
    **JD 与 resume_facts 分离**（断言标记位置关系）、空分段跳过、可复现。
- 旧稿逐字节比对：从实现提取的字面量与冻结文本 SHA-256 完全相同
  （`929d5f7e28ce418b…`），确认冻结合法。
- 实测发现并修复：第一版意图识别用前缀匹配，把「是的，帮我改一下」
  误判为 `fact_intake`（压制用户明确的改写要求），且「是……」被当成确认。
  改为整句匹配 + 排除省略号，并补 3 条回归测试。

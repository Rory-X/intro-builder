# Agent Note: 版本历史按任务聚合接到 UI，且不改既有文案

Status: implemented

## Problem

P06 任务 5 要求「列表**按任务聚合**，展开看各 revision 和 source；
**单条记录能回到 task/run**」。

投影层（`groupVersionsByTask`，25 例）与读取层（补齐 `runId`/`changeSetId`/
`mutationId`/`revision`）在前几个提交已完成，但 `version-history-popover.tsx`
仍用扁平的 `versions.map(...)` 渲染 —— 聚合结果**没有消费方**。

这带来的实际问题是可感知的：一次 Agent 任务常常产生多个版本
（多个工具各自提交一次），扁平列表把它们渲染成一串看不出关联的记录，
用户无法判断「哪几条属于同一次对话」。

## Decision

改成消费 `groupVersionsByTask`，但**约束两件事**。

### 1. 不改既有的单条渲染文案

「`N 处修改 · 操作人 来源`」这行已被 `version-history-popover.test.tsx`
的既有断言固定下来（`1 处修改 · Mem 通过对话`）。那是用户已经熟悉的表达，
本次改动的目标是**聚合与跳转**，不是重写措辞。

因此 `VersionRow` 的文案与原文逐字一致，既有的两条测试**不改动就通过**。
这是「向后兼容」的可验证证据，而不是口头承诺。

### 2. 未接线的入口不渲染

`onOpenRun` 与 `onUndo` 都是可选 props：

- 未传 `onOpenRun` 时**不显示**「回到对话」；
- 未传 `onUndo` 时**不渲染**撤销按钮（即使记录本身可撤销）。

理由：让用户点一个没接线的按钮比不显示更糟 —— 点了没反应会被理解成「功能坏了」。
测试对这两条各有一处断言。

撤销按钮还额外过滤 `canUndo(item)`：撤销记录本身（那是重做）、
无 `mutationId`（无法构造幂等键）、无主的系统操作都不显示。

### 3. 任务组默认折叠

plan 说「**展开**看各 revision 和 source」—— 展开是用户主动动作。
折叠时显示「N 次提交」与来源标签，让这一行不展开也有信息量。

组内含撤销记录时显示「含撤销」标记：撤销会让内容回到之前的样子，
用户看到「内容和我记得的不一样」时需要能确认原因，否则只能逐条点开找。

### 4. 缺失值显式收敛

`toRecord` 把 `undefined` 收敛成 `null`（旧数据与测试构造的对象可能没有
`revision`/`runId` 等字段）。这让既有测试**不需要改动**就能继续通过 ——
它们构造的对象没有这些字段，收敛后走「无 runId → 各自成组」的路径，
渲染结果与原来一致。

## 实测修正的三个测试问题（红 → 绿）

17 例中 2 例一开始失败：

**一、时间选择器不唯一**：组头显示**最新一次提交**的时间，展开后第一条子项
也是同一时间 —— `getByText` 命中两个。改用子项按钮的 `aria-label`
（带「N 处修改」后缀，与组头的「N 次提交」可区分）。

**二、我自己的测试写错了**：断言「有 runId 的组显示『回到对话』」，
但**没传** `onOpenRun` —— 而我的设计正是「未传则不显示」。
测试与实现冲突，说明断言写的时候没想清楚前置条件。修正为显式传 `onOpenRun`，
并把「未传时不显示」留给专门的一条断言。

## Alternatives considered

- **在组件里保留扁平渲染，另加一个「按任务分组」开关** — 两种视图都保留。
  否决原因：plan 要求的是「列表按任务聚合」，不是「提供聚合选项」。
  两个视图意味着两套测试与两条渲染路径，而默认哪个也是无谓的决策成本。
  聚合后「独立修改各自成行」已经覆盖了扁平视图的信息量。
- **改掉「N 处修改 · 操作人 来源」这行文案**（例如显示摘要）—
  信息量更大。否决原因：那是既有的用户可见文案，改它会让既有测试失效，
  而本次改动的目标里没有「改文案」。**我在上一个切片里正是因为没有守住这条
  而改了 `agent` 的来源标签，被 4 个测试抓出** —— 这次先看既有断言再动手。
- **投影层直接返回可渲染的结构（含 aria-label 文案）** — 组件更薄。
  否决原因：文案属于展示决策，放进投影层会让那个纯函数承担 UI 责任，
  且它的测试需要断言字符串（现在是断言结构化字段）。
- **撤销按钮总是渲染，未接线时禁用** — 用户能看到「有撤销这个功能」。
  否决原因：禁用的按钮不解释原因时同样是困惑源。若将来要提示
  「这条记录不支持撤销」，应当有明确的说明文案，而不是一个灰按钮。
- **`toRecord` 用 `as VersionRecord` 强转** — 少写 8 行。
  否决原因：强转会在 `undefined` 与 `null` 的差异上静默通过，
  而投影层的判空逻辑（`record.runId ? ... : ...`）对两者行为一致但语义不同。
  显式收敛让「旧数据没有这些字段」这件事在代码里可读。

## Consequences

- **收益**：用户能看到「哪几条属于同一次对话」并可展开；能跳回对话；
  可撤销的记录有入口（且不可撤销的不显示）；既有文案与测试不受影响。
- **代价**：组件从 85 行增至约 250 行；多一份 RTL 测试（17 例）。
- **已知上限**：
  - **`onOpenRun` 与 `onUndo` 在真实调用方处尚未接线**。组件支持这两个回调，
    但 `editor-client.tsx` 目前只传 `onSelectVersion` —— 因此界面上
    「回到对话」与「撤销」按钮**实际不会出现**。接线需要：
    ① `onOpenRun` 跳转到对话面板（跨组件状态，需要设计）；
    ② `onUndo` 接到撤销提交入口（**该入口本身也还没实现** ——
    `buildUndoCommand` 可用，但没有路由或 action 把「版本记录 → 撤销提交」串起来）。
  - **组内版本未排序展示为时间线**：展开后按投影的时间倒序，够用但未做
    「这次提交改了什么」的摘要展示（那需要结构化 Diff，已在
    `lib/resume-mutations/diff.ts` 就绪但未接入）。
  - 50 条上限未改（读取层既有行为）。聚合需要**完整列表**才能正确
    （跨页的同 runId 版本会被拆成两组）—— 目前没有分页，因此这个隐患未暴露。
- **什么信号发生时该重访**：若用户反馈「版本列表看不出哪几条是同一次对话」，
  先确认读取层是否真的取出了 `runId`（那是最可能的失效点）。
  若要实现跨页聚合，需要先让读取层按 `runId` 分组后再分页。
